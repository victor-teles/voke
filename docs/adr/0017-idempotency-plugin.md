# Idempotency is an opt-in Plugin backed by a table it provisions

AWS delivers events at least once, so a handler that charges a card must be safe to run twice. Voke ships this as `@voke/idempotency`, a separate package (ADR "Split provider and helper ownership into specialized packages"): core learns nothing about DynamoDB, and the package depends on public `voke`, `@voke/aws` and `@aws-sdk/client-dynamodb`. It is the first Plugin (ADR 0015) that contributes a resource.

- **Opt-in at the handler.** `idempotency()` in `voke.config.ts` makes nothing idempotent by itself. A handler opts in with `idempotent(handler, { key })`, or an SQS Function with `idempotentBatch(processMessage, { key })`. `key` is required and has no default (no JMESPath, no hash of the whole payload, no SQS message id): the **Idempotency Key** is a business decision, and a message id changes when a producer sends the same event twice.
- **How `idempotent` finds its store.** The Plugin's Function Wrap runs each handler inside a `node:async_hooks` `AsyncLocalStorage` scope holding the store, the Function key, the Function's timeout and the default expiry. There is no module-level singleton, so two Gateways in one process do not share state. Outside a scope `idempotent` throws a `VokeConfigError`; `idempotent(handler, { key, store })` skips the lookup for unit tests. This needed no core change: plan 019's wrap already runs around invokable, route, event and authorizer handlers, and in registry-only Lambda handlers composed with the config.
- **Record lifecycle** (the layout and conditions of Powertools for AWS Lambda): the record id is `<functionKey>#<name>#<sha256 of the key>`. One conditional `PutItem` writes `INPROGRESS` with `expiration` (epoch seconds) and `in_progress_expiration` (epoch milliseconds); it succeeds when no record exists, the record has expired, or it is `INPROGRESS` past its in-progress expiry. It returns the old item on failure (`ReturnValuesOnConditionCheckFailure: "ALL_OLD"`), so a blocked call needs no second read. A `COMPLETED` record with the same validation hash replays its stored JSON result; a different hash fails with `IDEMPOTENCY_PAYLOAD_MISMATCH`; a live `INPROGRESS` record fails with `IDEMPOTENCY_IN_PROGRESS`. A handler that throws deletes the record and rethrows. The default expiry is one hour.
- **The in-progress window is the Function's timeout** (`synthesis.timeout`, else `runtime.timeout`), read in `runtime.setup`. `InvokeContext` has no remaining-time value, which Powertools uses instead; when Voke exposes one, it replaces the timeout map.
- **The table is a Plugin Contribution**: `dynamodbTable({ partitionKey: "id", ttlAttribute: "expiration" })` under `idempotencyTable` (or `table`). `dynamodbTable` gained `ttlAttribute` for it. Like every resource, every Function role can read and write it and every Function gets its binding; per-Function resource linking (roadmap v2 phase 5) should narrow this. The DynamoDB client is imported and created on first use, so cold starts that never call an idempotent handler do not load it, and `@aws-sdk/*` stays external in the Lambda bundle.
- **Errors** are one `IdempotencyError extends Error` with four codes. It is not a `VokeError`, whose code union is closed in core. Messages never contain the key, the payload or the result.
- **Durable Functions are excluded.** Lambda replays a Durable Function's handler, so `idempotent` inside one would meet its own record on replay, and steps are already checkpointed. Starting one execution per operation is `functions.invoke(key, payload, { mode: "async", executionName })` (ADR 0014); the package writes no record for it. `@voke/aws` keeps its durable marker private, so the exclusion is documented, not enforced at run time.

To make `idempotentBatch` infer the message body inside `sqs({ handler: idempotentBatch(...) })`, `sqs()` became two overloads, one per `invalidMessageBody` mode. With one generic signature, the unresolved mode left the batch type deferred while the nested call was inferred, and the message body came out `unknown`. The runtime is unchanged.

Not covered: other stores (Redis, Valkey), a local cache in front of DynamoDB, HTTP status mapping for `IdempotencyError`, concurrent processing of one batch, and per-record forms for SNS, EventBridge, Kinesis and DynamoDB Streams.
