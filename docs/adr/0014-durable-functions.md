# Durable Functions: AWS Lambda durable functions are the orchestration model

Voke supports multi-step, long-running work through AWS Lambda durable functions and nothing else. `durable({ input, output, executionTimeout, handler })` from `@voke/aws` declares a **Durable Function**: an invokable Function whose handler receives `context.durable`, the SDK's `DurableContext`, and can checkpoint `step`s, `wait` for up to a year and pause for callbacks. Step Functions gets no builder and no workflow DSL; a project that needs a state machine declares it as a raw CloudFormation resource in `voke.config.ts` (the escape hatch of ADR "Specialized provider and helper packages"). This replaces roadmap-v2 phase 10's `workflow(...)` exploration: the same work is ordinary TypeScript, in the same deployment unit, with no second language.

`durable(...)` returns an ordinary invokable Function definition, so the Function Contract, `functions.invoke` typing, Function Contract Artifacts and Remote Function Registries need no change. Its durable settings travel in the existing `lambda.function` Provider Extension Record as `durable: { executionTimeoutSeconds, retentionDays? }`; `awsLambda()` does not accept them, so `durable(...)` is the one way to enable the feature. `executionTimeout` is required: a year-long default is a cost risk and a 15-minute default hides the feature. `@voke/aws` recognises a Durable Function by its stored handler, kept in a module-level `WeakSet`; the handler keeps its identity when `createFunctions` copies definitions.

The SDK's `DurableContext` is passed through unwrapped and re-exported as a type. Wrapping or renaming its surface would drift from AWS with every SDK release. `@aws/durable-execution-sdk-js` (3.0.0) is a dependency of `@voke/aws` and is bundled into Lambdas that need it; `@aws/durable-execution-sdk-js-testing` (1.3.2) is a dependency used only for local runs and tests and is never bundled.

## Local runs use the AWS testing runner (Strategy A)

A one-hour spike ran `LocalDurableTestRunner` under `bun test` with Bun 1.4.4: a `step` plus a 30-second `wait` completed in about 90 ms of real time with `setupTestEnvironment({ skipTime: true })` (the fake clock moved `Date.now()` by 30 s), a 1-second `wait` without `skipTime` took about 1 s, and a step with a retry strategy was retried until it succeeded, replaying the handler once per attempt. `AsyncLocalStorage` context set around the handler reached every replay. So Voke uses the runner (Strategy A) everywhere outside Lambda and does not maintain its own `DurableContext`; local runs replay exactly as Lambda does.

The runner needs `setupTestEnvironment` before any run. Voke starts it lazily with real time on the first local durable run (Gateway, `voke dev`, a test that did not opt in), so `wait({ minutes: 10 })` under `voke dev` waits ten minutes. Tests call `setupDurableTests()` / `teardownDurableTests()` from `@voke/aws/testing` to skip time; the runner's fake clock then also fakes `Date` and timers in that test file. The runner's checkpoint worker keeps a plain script alive until teardown; `bun test` and `voke dev` are unaffected. `runDurable(functions, key, payload)` invokes through `functions.invoke` (so contracts are validated) and returns the result with the SDK's recorded operations. Locally the user handler receives the already-parsed payload through a closure, and a failed execution rejects with the error the handler last threw (for a failed step, the SDK's `StepError`).

## Deployment: a retained version behind the `live` alias

Durable functions must be invoked with a qualifier, and an execution is pinned to the version that started it; `$LATEST` would resume paused executions on new code. Each Durable Function therefore gets an `AWS::Lambda::Version` with `DeletionPolicy: Retain` and `UpdateReplacePolicy: Retain`, and an `AWS::Lambda::Alias` named `live` that points at it. The version's logical id ends in a hash of the Function's synthesized properties, which include the bundle key, so every code or configuration change publishes a new version and old versions keep serving their executions. Retained versions accumulate (one per Durable Function per changing deploy); pruning is a follow-up.

The Function's role gets `lambda:CheckpointDurableExecution` and `lambda:GetDurableExecutionState` on `arn:aws:lambda:<region>:<account>:function:<name>:*`; an unqualified ARN never matches an execution ARN. Every Function in the stack gets `VOKE_INVOKE_TARGET_<KEY> = <deployedName>:live` for each Durable Function and `lambda:InvokeFunction` on those aliases, matching the current model where every Function reaches every declared resource. All these ARNs are built from deployed names, not `Fn::GetAtt`, so roles do not depend on Functions. A stack without Durable Functions synthesizes exactly as before.

Lambda enables durable execution only when it creates a function, and CloudFormation cannot replace a named resource. Before executing a change set, `voke deploy` fails with a `VokeDeployError` when an `AWS::Lambda::Function` change has `Replacement: "True"`, and deletes the change set; `--dry-run` prints the same condition as a warning.

## The deployed handler goes through `functions.invoke`

A Durable Function's Lambda handler is `withDurableExecution((event, durableContext) => ...)` that sets the execution's `DurableContext` as the ambient context (`AsyncLocalStorage`) and calls `functions.invoke(key, event, { runtime: "local" })`. The stored handler finds the ambient context and calls the user handler with it. Input parsing, Runtime Variables and output parsing are the same code as local runs and run on every replay, and Provider plugins that wrap `functions.invoke` cover Durable Functions with no durable-specific code. The SDK is loaded with `import()` on the first durable invocation, so other cold starts never evaluate it, and the AWS build plan marks it external for projects without Durable Functions so their bundles do not grow.

## A neutral invoke hook in core

Deployed, `functions.invoke` runs targets in-process, which would make a Durable Function started from another Lambda not durable at all. Core gains a provider-neutral hook and no durable vocabulary:

- `ProviderInvokeCapability.target({ key, definition })` returns `{ functionName }` when the Function must be invoked through the Provider's `transport()`. Core then sends the bare parsed payload (no `{ payload, trace }` envelope) and uses the response payload as returned (no `{ data }` unwrapping). An explicit `runtime` skips the hook, and the existing `runtime: "aws"` path is unchanged.
- `ProviderInvokeCapability.acceptsExecutionName({ key, definition })` says which Functions accept `InvokeOptions.executionName`. A routed call forwards it as `InvokeRequest.executionName`; an in-process run of an accepting Function ignores it, so the same code works locally and deployed; any other Function rejects it with `InvokeError` code `INVALID_OPTIONS`. The plan rejected the name on every non-routed call, which would have made `voke dev` reject code that works deployed.
- `AsyncInvokeResult.executionId` and `InvokeTransportResponse.executionId` carry the execution the Provider started.
- `activateFunctionRegistry(registry, key, { invoke })` stores the capability; `voke(...)` passes `config.provider.invoke`, and the registry-only Lambda path passes the AWS capability.

`aws()` routes a Durable Function when `VOKE_INVOKE_TARGET_<KEY>` is set (deployed only) and maps `executionName` to `DurableExecutionName` and `DurableExecutionArn` to `executionId`. `mode: "async"` uses `Event` (executions up to the execution timeout); the default `RequestResponse` is capped at 15 minutes.

## Not yet proven

The deployed path has not run on real AWS. Open until a smoke deploy: that the managed Node.js runtime's `@aws-sdk/client-lambda` (kept external) contains the durable commands the SDK imports on first checkpoint, and that core's pre-handler work (schema parsing, Runtime Variable loading) does not trip the SDK's suspension rules into re-execution loops. Event Sources cannot target a Durable Function; an Event Source Function starts one with `functions.invoke(key, payload, { mode: "async" })`.
