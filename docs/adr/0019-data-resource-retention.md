# Keep tables, buckets and secrets unless the user says otherwise

Voke derives each resource's CloudFormation logical id from its resource key and lets AWS generate the physical name. Before this decision no resource had a `DeletionPolicy`, so renaming a key, changing a table's `partitionKey` or `sortKey`, deleting the entry, or running `voke remove` made CloudFormation delete a populated table, bucket or generated secret without a warning.

A **Data-Bearing Resource** holds state that exists nowhere else and that a redeploy cannot recreate: `dynamodbTable()`, `s3Bucket()` and `secret()` (a generated secret value qualifies). `sqsQueue()` and `kinesisStream()` carry records in transit with a bounded lifetime, and a retained queue has no consumer while a retained stream is billed by the hour; `snsTopic()` and `eventBus()` store nothing; `ssmParameter()` takes its value from the config. These are not data-bearing. The builder sets `dataBearing: true` in its AWS **Provider Extension Record**, so the marker stays in `@voke/aws` and core is unchanged.

Synthesis gives each data-bearing resource `DeletionPolicy: Retain`, `UpdateReplacePolicy: Retain` and the metadata entry `VokeRetain: true`, on every stage. CloudFormation applies a policy change only together with another change; the metadata entry is that change. Raw resource definitions in `resources` carry no marker and pass through untouched, whatever their type: the escape hatch stays a literal CloudFormation definition. Local AWS Providers synthesize with retention off, because local data is disposable and a retained resource in Floci, which binds resources by logical id, would block the next create.

There is one opt-out: `aws({ retainData })`, `true` by default, `false`, or a predicate over `{ key, stage, type }`. It lives on the Provider, not on the builders, because retention must be decided with the resolved stage and `voke.config.ts` runs before the CLI applies `--stage`. A builder option would be stage-blind and push projects to read `VOKE_STAGE` by hand. There is no CLI flag for retention.

Before it executes a change set, `voke deploy` refuses any change that removes a data-bearing resource or replaces it (`Replacement` `True` or `Conditional`), whether CloudFormation would keep or delete it, because in both cases the Functions lose their data: they are bound to a new, empty resource or to none. The check reads types from the change set, so it also guards raw definitions. The refusal deletes the change set and names each resource and its fate from `PolicyAction`. `voke deploy --accept-data-loss` is the one override, per run and never a config setting; core passes it to the Provider as `acceptDataLoss`. `--dry-run` never refuses and prints the same lines as warnings. Every change set runs with `RetainExceptOnCreate`, so a failed deploy that rolls back leaves no new, empty retained resource.

`voke remove` takes no new flag and never deletes retained data. It deletes the stack, then lists each data-bearing resource CloudFormation skipped (`DELETE_SKIPPED`) with its physical id and the command that deletes it. To destroy a stage's data with its stack, the user sets `retainData` to `false` for it, deploys, then removes. Adoption is manual: delete with the printed command, copy the data into the new resource, or use CloudFormation resource import.

The trade-off is deliberate. A **Retained Resource** is no longer managed by any stack and AWS bills it until someone deletes it; in exchange, no rename, key change or remove deletes data silently. A stack deployed before this decision is protected only after one deploy that keeps the resource, because CloudFormation applies the policy of the deployed template.
