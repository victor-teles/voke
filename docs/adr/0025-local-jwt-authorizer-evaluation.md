# Local Authorizer Evaluation enforces JWT Authorizers without verifying signatures

ADR 0006 said Local Authorizer Evaluation "does not fully validate JWTs by default" but did not say what it does check. The code skipped JWT Authorizers entirely: under `voke dev`, `gateway.request(...)` and `createTestClient(...)` a route behind a JWT Authorizer ran without a token, and its handler saw `{ context: {}, source: "lambda" }`. A protected route was open locally, nothing local ever answered 401, and a handler that reads claims could not be exercised over HTTP. A route that named an authorizer missing from its registry also ran open. This ADR defines "not fully".

- **What is checked.** The local Gateway reads the token from the authorizer's single Authorizer Identity Source (`$request.header.<name>` or `$request.querystring.<name>`), removes an optional `Bearer` prefix, and requires three dot-separated segments whose first two are base64url JSON objects. It then checks, with no clock leeway: `iss` equals the configured issuer exactly; `aud` contains a configured audience, or `client_id` does when `aud` is absent; `exp` is a number after now and is required; `nbf` and `iat`, when present, are numbers at or before now. Being stricter than API Gateway where AWS is silent costs a local 401 the developer sees at once; being looser would hide a deployed 401.
- **What is not checked.** The signature, the `alg` and `kid` header values, and scopes (Voke has no route scopes). No JWKS is fetched and no key material is used. A passing local test therefore does not prove that a token is genuine, or that the issuer's keys are reachable from API Gateway.
- **Failures** answer 401 with Voke's Error Envelope (`UNAUTHORIZED`). The reason goes in `www-authenticate` (RFC 6750 `invalid_token` with a fixed description), never a token or claim value. A route naming an unknown HTTP Authorizer answers 500 with the message synthesis uses.
- **Claims are strings.** The Route Auth Context is `{ context: claims, source: "jwt" }` with every value rendered as API Gateway passes it: numbers and booleans as strings, arrays as `[a b]`, other values as JSON. AWS does not document this rendering; it follows reported behaviour and lives in one function so it can be corrected after a real-stage check.
- **Never for a platform-delivered request.** A new optional Provider Capability member, `ProviderRuntimeCapability.isPlatformRequest`, reports that the platform invoked a deployed Function. When it is true and `routeAuth` reported nothing for a JWT Authorizer route, the Gateway answers 401 instead of accepting an unsigned token. The AWS Provider implements it as "the Lambda event is present". A new Provider must implement it too.
- **It lives in core.** Local Authorizer Evaluation, `JwtAuthorizerDefinition` and the Route Auth Context are core concepts, and the Gateway evaluates authorizers with no Provider configured. The module uses only Web-standard globals and imports no `@voke/*` package, so ADR 0007's boundary holds. It is not exported.
- **Tests mint tokens with `createTestJwt(authorizer, claims?)` from `@voke/testing`.** It returns an unsigned (`alg: "none"`) token whose issuer and audience come from the authorizer, so they cannot be mistyped. API Gateway rejects it.
- **Lambda Request Authorizers** now read header, query string and `$context` identity sources locally; `$stageVariables` counts as missing because Voke stages define none. `jwtAuthorizer()` throws `VokeConfigError` unless it has exactly one header or query string identity source.
