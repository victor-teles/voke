# A Function reaches only the resources it links

Voke synthesized one IAM role per Function, but every role got the statements of every resource in `voke.config.ts`, and every Lambda got every `VOKE_RESOURCE_*` binding, so a bug in one route handler could read and write every table, queue, bucket and secret of the stack. A Function now declares the resources it uses with a **Resource Link**, reads them through its handler context, and its role and environment hold those resources and no others. An unlinked read fails the same way under `voke dev`, in tests and on AWS.

- **One spelling**: `resources: ["<resource key>", ...]` on every Function builder: `fn`, `http`, `requestAuthorizer`, `durable`, `sqs`, `sns`, `eventBridge`, `schedule`, `kinesis`, `dynamodbStream` and `s3`. It mirrors `variables` and uses the resource key, like every other reference from a Function to a resource (`queue: "ordersQueue"`, `fromResource("signingSecret")`). The model carries `links` per Function, and `bindings` becomes per Function: one per link, then one per resource a Runtime Variable reads.
- **One way to read**: `context.resource("<resource key>")` returns the binding value as a string. `bindResource` and `ResourceBinding` are removed from `@vokejs/aws` without an alias: an ambient read of `process.env` cannot know which Function is running, and it is why an unlinked read used to pass locally. Code outside a handler takes the value as an argument.
- **Typing**: a Function's own `resources` types the keys its handler may read; `context.resource(key)` is declared with method syntax so a handler annotated with the plain `InvokeContext` still fits. That a key exists in the config is checked when the model is built, with a `VokeConfigError` at `functions.<name>.resources.<index>`.
- **Errors**: an unlinked read throws `VokeResourceBindingError` naming the missing link, in every environment. The checks run when the handler reads: the Function links the key; the entry Function links it (below); the registry was activated with a config; the variable is set.
- **In-process invocations use the entry Function's links.** `functions.invoke` runs a local handler in the caller's process, with the caller's deployed role and environment, so a read must be linked by both the running Function and the Function entered first. Core tracks the entry with one `AsyncLocalStorage`; an invocation that leaves the process (the `aws` runtime, or a Function the Provider routes through its transport, such as a Durable Function) starts a new entry.
- **An Event Source grants its Function what the trigger needs on the source resource, and nothing else.** The SQS adapter adds `sqs:ReceiveMessage`, `sqs:DeleteMessage` and `sqs:GetQueueAttributes` on its queue; Kinesis and DynamoDB streams keep their read statements; SNS, EventBridge, S3 and schedule need none. A handler that also sends to its queue, reads the uploaded object or writes the table links the resource.
- **A `fromResource(key)` Runtime Variable keeps working without a link**: the Function gets the resource's read statement and binding, but not `context.resource(key)`.
- **A Plugin Contribution resource is linked like any other.** A Function that uses `idempotent` or `idempotentBatch` declares `resources: ["idempotencyTable"]`; the Plugin reads the table name through `execution.context.resource(table)` once per handler call, and `idempotentBatch` does so before its message loop, so a missing link fails the invocation.
- **`awsPolicy()` statements stay on every Function role**, because a Plugin's Function Wrap runs around every Function and the statements are written explicitly in the config.
- **`http({ routes })` is one Function**, so its links cover all its routes. A route is not a deployable unit and IAM could not enforce a per-route link.
- **A link grants the builder's full action list.** `dynamodbTable()` gains `dynamodb:BatchGetItem`, `dynamodb:BatchWriteItem` and `dynamodb:ConditionCheckItem`; a transaction needs no action of its own, because DynamoDB authorizes each item with its item action.

`voke dev` keeps every binding in its one process environment, so the check lives in `context.resource`, not in the environment. The first deploy after this change removes statements and variables from existing roles and Lambdas in place; a Function that relied on the blanket grant fails closed.

## This decision reverses earlier ones on purpose

- _Contradicts ADR "A typed Plugin contract covers run time and deploy time": "IAM statements added to every Function role, matching how resource statements are scoped today" — but worth reopening because_ resource statements are no longer scoped that way. `awsPolicy()` keeps its every-role scope for a reason of its own (a Function Wrap runs around every Function), not to match resources.
- _Contradicts ADR "Idempotency is an opt-in Plugin backed by a table it provisions": "Like every resource, every Function role can read and write it and every Function gets its binding" — but worth reopening because_ stored handler results should be readable only by the Functions that write them, and that ADR already named per-Function linking as the way to narrow it.
- _Contradicts ADR "Runtime Variables and AWS export boundaries", which lists `bindResource` among the runtime helpers of `@vokejs/aws` — but worth reopening because_ an ambient binding read cannot be checked against the running Function. That ADR's own pattern, per-Function declarations read from the handler context for least-privilege IAM, now covers resources too.

## Not covered

- Resource keys are not typed against `voke.config.ts`: a key misspelled the same way in `resources` and in `context.resource`, or linked and never read, is a model error at `voke dev`/`synth`/`build`/`deploy`, not a compile error. Typing it needs a generic `defineConfig`, typed Plugin Contribution keys and a registration line per config, and would also cover `queue`, `bucket` and `fromResource`; it is a separate change.
- A `voke resources` command, a per-Function custom-statement escape hatch, read-only links, migration hints that turn Serverless IAM statements into links, and a `config` option for `createInvokeTestClient`.
- Runtime Variables have the same in-process gap that entry tracking closes for resources: a callee's variable is loaded with the caller's role.
