# A typed Plugin contract covers run time and deploy time

Voke adds one extension contract, the Plugin: a plain object (`VokePlugin`) built by a factory function and declared only in `voke.config.ts` as `defineConfig({ plugins: [a(), b()] })`. `voke()` takes no `plugins` option, so a project has one place that says which Plugins it runs. A Plugin has a `name` matching `^[a-z][a-z0-9-]*$` and up to three optional capabilities:

- `runtime.setup({ config, dev, functions })` runs once when a Gateway is composed and returns Gateway `middleware` and a Function Wrap, `wrap(execution, next)`. The wrap runs around the handler call of every invokable, route, Event Source and Request Authorizer Function of the activated Function Registry, including Plugin Functions and any Function that a deployed handler reaches through `functions.invoke`. It sees the parsed input and the handler result before output validation; `next` takes no arguments, so a wrap cannot change the input. The first Plugin is the outermost wrap. A wrap may short-circuit, and its value is then validated like a handler result; calling `next()` twice rejects. A registry activated without a config (`createInvokeTestClient(functions)`, `createLambdaHandlers({ functions })`) runs without Plugins, and with no wraps the handler is called directly.
- `contributions` is static data: `resources` and `environment` merged into the config (a key the project or another Plugin already holds with a different value is a config error), `provider` Provider Extension Records copied untouched to `model.plugins[<name>].provider`, and route-backed `functions` keyed `<plugin>-<name>`. Plugin Functions stay outside the typed Function Registry; one core helper, `projectFunctionEntries(functions, config)`, adds them after the project's Functions for the Gateway, the model, `voke build` and `createLambdaHandlers`.
- `cli.commands` adds `voke <plugin> <command>`. Built-in commands win, so a Plugin with `cli` cannot take a built-in command name or `help`.

Provider-specific contributions go through Provider Extension Records that the Provider validates (ADR "Split provider and helper ownership into specialized packages"). The AWS Provider accepts `awsPolicy({ statements })`, IAM statements added to every Function role, matching how resource statements are scoped today. So that a registry-only project gets its Plugins in Lambda, `voke build` imports the config file into the generated entry and calls `createLambdaHandlers(project, { config })`, which composes the Gateway from it; a Gateway export must have been created with the same Plugins.

This decision reverses two earlier ones on purpose:

- _Contradicts `roadmap-v2.md`, "Explicit Non-Goals": "Do not introduce a broad plugin API before first-party runtime behavior is stable", and its principle "Favor built-in boring defaults over plugin ecosystems for critical runtime behavior" — but worth reopening because_ the deploy path works, the Provider contract has proved that capability objects in `voke.config.ts` are a workable extension shape, and the next integrations (OpenAPI, idempotency) each need runtime hooks plus deploy-time contributions. Without a contract they would be hard-wired into core.
- _Contradicts ADR "Voke is an opinionated framework with one escape hatch per layer": "Each layer keeps exactly one escape hatch […] Hono middleware on the Gateway for HTTP behavior" and "New options should be added only when a use case cannot be met through the default or the layer's escape hatch" — but worth reopening because_ Hono middleware reaches only HTTP routes, and no existing escape hatch can add a deployed route, a resource or a command. The Plugin contract is one new supported way, not a second spelling: `voke(functions, { middleware })` and `route.use(...)` stay the direct HTTP escape hatch.

What a Plugin cannot do in v1: replace or wrap the Provider; edit the synthesized template; change a Function Contract or the handler input; observe input or output validation failures; contribute invokable, event or authorizer Functions (the deployed handlers for those call the user's typed registry, which cannot hold Plugin keys); add flags to built-in commands; see the stage or project name when it builds its contributions. Runtime Variable providers keep their own contract. A Plugin's `cli` code is bundled with the deployed handlers because the config is imported at run time, so command-only dependencies belong behind `await import(...)` inside `run`.
