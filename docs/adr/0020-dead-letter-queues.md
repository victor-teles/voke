# Failed events go to a dead-letter queue by default

Before this decision no Event Source had a failure path. An SQS message that could never succeed was delivered again until the queue's retention ended (4 days by default), each delivery a paid invocation. A stream record that could never succeed blocked its shard until it expired. An SNS, EventBridge, S3 or schedule event that failed was retried twice by Lambda and then dropped. A user found out from a missing side effect.

Every Event Source the AWS Provider supports now sends an event its Function cannot process to an SQS queue that Voke creates, on every stage, without being asked. The **Dead-Letter Queue** is a standard queue with `MessageRetentionPeriod` 1,209,600 seconds (14 days, the maximum; a standard queue keeps a message's original enqueue time, so it must outlast the source queue's 4 days). It has no name (CloudFormation generates one), no KMS key (SSE-SQS is the default), no binding, no stack output and no IAM for user code.

Who owns the queue follows where AWS puts the failure setting. An SQS queue has one redrive policy and may be consumed by several Functions, so for SQS the **source queue** owns it: every queue that at least one Function in the project consumes gets `<QueueLogicalId>DeadLetterQueue` and a `RedrivePolicy` with `maxReceiveCount` 5, the minimum the Lambda Developer Guide recommends ("configure a dead-letter queue on the Amazon SQS queue itself and not on the Lambda function"). SQS moves the message itself, so no role statement is added. A queue nobody in the project consumes is left alone, because its consumer is elsewhere. A hand-written queue whose properties already contain `RedrivePolicy` is left untouched: that is the escape hatch for a different receive count. A hand-written FIFO queue gets a FIFO dead-letter queue so the stack still deploys; FIFO is otherwise out of scope. There is no `RedriveAllowPolicy`, because naming the source queue there would make the two queues depend on each other.

For every other source the failure path is a Lambda setting of one Function, so the **Function** owns the queue: `<FunctionLogicalId>DeadLetterQueue`.

- Kinesis and DynamoDB stream mappings get `DestinationConfig.OnFailure` pointing at the queue, and `MaximumRetryAttempts` defaults to 10 when the queue is on. This supersedes the `MaximumRetryAttempts` paragraph of ADR 0012: with a destination a capped mapping no longer discards records silently, so a bad record leaves the shard after ten retries instead of blocking it for a day. Bisecting stays on and does not consume retries, and ten is larger than a short downstream blip. `maxRetryAttempts` still overrides it, and `-1` still means "until the record expires". Without a dead-letter queue `MaximumRetryAttempts` stays unset, as before. An SQS destination receives only metadata: the stream ARN, shard id and first and last sequence numbers. The records must be read from the stream before its retention ends (24 hours for DynamoDB Streams and for `kinesisStream()` without `retentionHours`). An S3 destination would keep the payload but adds a bucket to manage; it is deferred.
- SNS, EventBridge, S3 and schedule Functions get an `AWS::Lambda::EventInvokeConfig` on `$LATEST` with an `OnFailure` destination. Lambda's defaults (two retries, six hours) are kept and not exposed. The older Function `DeadLetterConfig` is not used, because the destination record also carries the response and the reason.
- Schedules also set `Target.DeadLetterConfig` to the same queue, so an invocation EventBridge Scheduler could not deliver is kept too. Scheduler sends with the schedule's execution role, so `VokeSchedulerRole` gets `sqs:SendMessage` on the scheduled Functions' queues (EventBridge Scheduler User Guide, "Configuring a dead-letter queue").

For streams and asynchronous sources Lambda sends as the Function's execution role, so that Function's role, and no other, gets `sqs:SendMessage` on its own queue through the adapter's `roleStatements`. No Function can read any dead-letter queue.

There is one opt-out spelling, `deadLetterQueue: false`, written on the owner: `sqsQueue({ deadLetterQueue: false })` for SQS and `kinesis | dynamodbStream | sns | eventBridge | s3 | schedule({ deadLetterQueue: false })` for the rest. `sqs()` has no such option, there is no `aws({ ... })` switch, and there is no option to pass a queue of your own. `sqsQueue()` records the opt-out in its AWS **Provider Extension Record**; the other builders always store `deadLetterQueue: true | false` in their Event Source properties.

A dead-letter queue is not retained (ADR 0019): no `DeletionPolicy`, no `UpdateReplacePolicy`, no `dataBearing` marker, the same as `sqsQueue()`. Its messages expire after 14 days anyway, a retained queue with a generated name would be orphaned on every Function or queue rename, and the data-loss pre-flight would then refuse every removal of an Event Source Function. The cost: renaming or removing the owner, or setting `deadLetterQueue: false`, deletes the queue and its messages, so they must be drained first.

The resources cost CloudFormation's 500-per-stack budget: one per consumed queue, one per stream Function, and two per SNS, EventBridge, S3 or schedule Function (the queue and the `EventInvokeConfig`). It is documented, not enforced. A declared resource whose key maps to a dead-letter queue's logical id fails synthesis, because adapter resources no longer overwrite template resources silently.

Local runs do not change: `functions.sendEvent` returns the batch result or throws, and nothing retries or dead-letters. The resources-only template that `voke local bootstrap` deploys has no dead-letter queue and no `RedrivePolicy`, because no adapter runs for it. Reading and redriving is documented, not built: the SQS console's "Start DLQ redrive" (or `aws sqs start-message-move-task`) works only for a queue SQS itself dead-lettered from another queue; events from the other sources are re-published or re-invoked by hand.

This supersedes the DLQ deferral of ADR 0003, the "dead-letter queues, Lambda `OnFailure` destinations" deferral of ADR 0011 and the `MaximumRetryAttempts` paragraph of ADR 0012. Still deferred: SNS subscription `RedrivePolicy` and EventBridge target `DeadLetterConfig` (each needs an `AWS::SQS::QueuePolicy` and covers only Lambda refusing the invoke call), S3 failure destinations, a configurable `maxReceiveCount` or retention, a user-supplied queue, bindings to read a dead-letter queue from code, a `voke` redrive command, alarms on queue depth, FIFO support, and asynchronous `functions.invoke`, which is not an Event Source.
