# Remote Function Registries live in `@vokejs/remote`; the project side lives in `voke`

The code for calling another Voke Project existed twice, in `packages/core/src/remote.ts` and `packages/remote/src/index.ts`, and each copy was half dead: core's config, CLI and Gateway called core's copy of the project side, while generated modules imported the untested client from `@vokejs/remote`. Each piece now exists once, split by caller. Core keeps the project side that its own config, CLI and Gateway call synchronously: the **Function Contract Artifact** (`createFunctionContractArtifact`, `toContractJsonSchema`, the fingerprint), remote config (`defineRemoteConfig`, `remoteEnvironment`), **Remote Code Generation** and the **Dev Function Invoke Endpoint**. `@vokejs/remote` keeps the **Remote Function Registry**: `createRemoteFunctions`, its types, the JSON Schema check and the origin lookup. A re-export is impossible in either direction: core must not import `@vokejs/*` packages (they depend on core), and `@vokejs/remote` can import only the root of `voke`, where `createRemoteFunctions` does not belong. This refines [ADR 0007](./0007-specialized-provider-and-helper-packages.md) for a helper whose CLI and Gateway halves must stay in core. The wire pieces (the path `/_voke/functions/<key>/invoke`, the request `{ contractFingerprint, payload, trace }` and `VOKE_REMOTE_<NAME>_ORIGIN`) are spelled once per side and held together by tests, not by a shared export.

`@vokejs/remote` exports one runtime symbol, `createRemoteFunctions`, with the types `RemoteFunctionRegistry` and `RemoteInvokeOptions`. `createFunctionContractArtifact`, `defineRemoteConfig`, `generateRemoteModules`, `mountDevFunctionEndpoints`, `remoteEnvironment` and `renderRemoteModule`, and the types `RemoteTarget`, `VokeRemoteConfig`, `VokeRemoteConfigInput` and `GenerateRemoteOptions`, are removed from it without aliases ([ADR 0007](./0007-opinionated-framework.md): the package is unreleased). The one supported way to do each is `voke remote generate`, `remotes` in `voke.config.ts` and the Gateway under `voke dev`. `toContractJsonSchema` leaves the root of `voke`, because its only outside user was the deleted copy; the root exports the artifact types instead (`FunctionContractArtifact`, `FunctionContractMetadata`, `ContractJsonSchema`).

A failed remote call always rejects with an `InvokeError`, never a raw `SyntaxError`, `TypeError` or `DOMException`. The documented codes are kept: a non-2xx answer is `TRANSPORT_FAILED` (404 is `MISSING_FUNCTION`) with `statusCode`, contract drift is `TRANSPORT_FAILED` with `statusCode: 409`, a request that fails is `TRANSPORT_FAILED` with the cause, a 2xx answer without a data envelope is `TRANSPORT_FAILED`, and a missing runtime target stays a `VokeConfigError`. A registry accepts `trace`, `timeoutMs` (bounds each attempt and cancels its request) and `retries` (repeats only a timeout, a failed request or a 5xx answer, without delay); every other option, `mode` included, is a type error and rejects with `INVALID_OPTIONS`, because the endpoint has no asynchronous mode. The Dev Function Invoke Endpoint answers 400 `BAD_REQUEST` to a body that is not a JSON object. Deferred: a dedicated contract-drift code and `TRANSPORT_STATUS_ERROR` for non-2xx answers (both change `InvokeErrorCode`), forwarding the provider project's `InvokeError` code through the endpoint, `issues` on remote validation errors, asynchronous remote calls, deployed cross-project invocation and endpoint tokens ([ADR 0004](./0004-contract-metadata-remote-functions.md)), a two-project example, and merging `@vokejs/http` with core's response helpers, which stay identical copies pinned by a test.
