# Pass plain query and headers to routes and answer client mistakes with 4xx

A route's **Route Request** carries `query` and `headers` as plain objects, with or without a schema. Without a schema both are typed `Record<string, string | undefined>`; with one, the schema receives the plain object and the handler gets its output. The original `Request`, with its `Headers`, stays at `raw`. One shape means that adding a schema never changes what kind of object the handler holds, and it is the shape the OpenAPI document already describes and the shape of the HTTP API payload v2 event. Before this, schemas received a `URLSearchParams` and a `Headers` instance, so an object schema rejected every real request.

Header names are lower-case, because `Headers` and the HTTP API both deliver them that way. `functions.route(...)` lower-cases the names it is given, so a test behaves like a request, and a `@voke/schema` object used as a `headers` schema with a name that is not lower-case fails Gateway composition with a `VokeConfigError`. Other validators cannot be checked; the guide states the rule.

A repeated query key or header is one string, combined with a comma (`?tag=a&tag=b` gives `"a,b"`); cookies are joined with `; `. Values are never arrays. One value type keeps `Record<string, string>` and `schema.string()` true for every request, matches the HTTP API's own `queryStringParameters` and `headers` fields, and avoids an "array only when repeated" shape that breaks `z.array(...)` for a single value. A route that must tell a repeated key from a value containing a comma reads `request.raw.url`.

A `body` schema means a JSON body. No body or an empty body gives the schema `undefined`. A media type of `application/json` or `application/<anything>+json`, compared on the type before `;`, trimmed and lower-cased, is parsed as JSON. JSON that does not parse is a 400 with the single issue `Malformed JSON` at `["body"]`; the parser's own message is never used, because it differs between Bun and Node and local and deployed answers would differ. Any other or missing content type with a non-empty body is a 415. Passing a text body to the schema is removed: it produced a misleading "Expected object", and a route that takes text, a form or binary data declares no `body` schema and reads `request.raw`.

`query` is validated as sent, so a strict schema (every `@voke/schema` object) rejects an undeclared query parameter. A `headers` schema that exposes its keys receives only those headers, because clients, proxies and API Gateway always add headers the route did not declare; any other validator receives all headers, so a strict object schema from another validator cannot be used for headers.

A wrong method stays a 404 `NOT_FOUND`, with no 405 and no `Allow` header. The deployed HTTP API has one route key per declared method and path, so API Gateway answers 404 for another method before any Function runs; a local 405 would make `voke dev` and tests disagree with production. A 405 needs an `ANY <path>` route in HTTP API synthesis and a Gateway change together.

Every error the Gateway writes is an **Error Envelope** with a `code`: 400 `INVALID_REQUEST` with `issues` for a request part that fails its schema or a malformed JSON body; 415 `UNSUPPORTED_MEDIA_TYPE`; 404 `NOT_FOUND`; an `HTTPException` below 500 with its own status, a code from the status and its message (one with `res` is returned unchanged); and 500 `INTERNAL_SERVER_ERROR`, `Internal server error`, for everything else, with `details.message` under `voke dev` only. Input issues describe the client's own request and are returned with the validator's messages and the part as the first path segment. An output that fails its schema is a server failure: its issues go to the one JSON log line and the client gets the generic 500.

A request failure is decided by where it happened, not by the error's class. Only an error thrown while the Gateway builds the Route Request for the route it matched is a client error. An `InvokeError` thrown inside the handler, from a nested `functions.invoke` or `functions.route`, is a server failure whatever its code, so the internal Function name and field names never reach the client. This replaces matching error messages with regular expressions. `functions.route(...)` keeps throwing `InvokeError` with full issues, because its caller is the developer's test, not an HTTP client.
