# A retried handler runs once on the idempotency failure paths, and the caller gets the real error

ADR 0017 kept "run once" on the happy path. Four failure paths broke it: a handler that ran longer than `expiresAfterSeconds` could run a second time while the first was still running; a result the store could not hold made every retry run the handler again; a failing delete hid the handler's own error; and `idempotentBatch` swallowed every error, so a missing Plugin or an `AccessDenied` on the table failed each message with no trace. This ADR amends ADR 0017's record lifecycle and error list.

- **An in-progress record expires no earlier than its in-progress window.** Acquire writes `expiration = max(start + expiresAfterSeconds, ceil(in_progress_expiration / 1000))`. `expiration` is also the time-to-live attribute, so the stored value itself must be right; a status-aware condition alone would still let DynamoDB delete a running record. A completed record still replays for exactly `expiresAfterSeconds`.
- **The acquire condition is unchanged**, the same three clauses as Powertools. With the expiry above, `#expiration < :now` is true for an `INPROGRESS` record only after its in-progress window. Acquire stays one conditional write.
- **`expiresAfterSeconds` is not compared with the Function timeout.** A shorter value is a legitimate short replay window, and the expiry rule makes it safe.
- **A result too large to store is recorded, not retried.** The limit is 350 KB of UTF-8 JSON (`maxResultBytes`), checked for every store, leaving room under DynamoDB's 400 KB item limit. Over it, the record becomes `RESULT_TOO_LARGE` through a new store method, `markResultTooLarge(id, expiresAt)`, with the expiry of a completed record. The first call and every retry until expiry reject with `IDEMPOTENCY_RESULT_TOO_LARGE`; the handler does not run again. A payload mismatch is reported before this status. `IDEMPOTENCY_RESULT_NOT_SERIALIZABLE` keeps releasing the record.
- **A failed completion write has its own error and is not retried by the package.** The SDK client already retries throttles and transient errors; a backoff loop would need the remaining execution time, which `InvokeContext` lacks. When `complete` or `markResultTooLarge` rejects, the call rejects with `IDEMPOTENCY_COMPLETE_FAILED` and the store's error as `cause`. The record stays `INPROGRESS`, so retries get `IDEMPOTENCY_IN_PROGRESS` until the Function timeout passes, then run the handler again. That residue is inherent: the store could not be written. The handler's result is not returned, as that would hide the store failure.
- **The handler's error wins over a failed delete.** The handler's error object is rethrown unchanged (same identity, so the Gateway's status mapping still works). The delete failure is logged once with `console.error`, naming the Function. No `AggregateError`, which would change the type callers catch.
- **`idempotentBatch` fails a message only for message-scoped errors.** Those are an error thrown by `processMessage`, and `IDEMPOTENCY_IN_PROGRESS`, `IDEMPOTENCY_PAYLOAD_MISMATCH` and `IDEMPOTENCY_KEY_MISSING`. Every other error (a store error, a missing link or Plugin, `IDEMPOTENCY_COMPLETE_FAILED`, a `key` or `validate` that throws) is rethrown, so the Event Invocation fails, Lambda logs it and SQS redelivers the batch; completed messages replay as successes. A payload mismatch belongs to one message and must not hold back its batch-mates. Messages that keep failing reach the dead-letter queue (ADR 0020).
- **A failed message is logged, except an in-progress duplicate.** `idempotentBatch` calls `console.error` with the SQS message id and the error. The package's own messages still never contain the key, the payload or the result; the logged error is the project's own. An in-progress duplicate is the expected outcome and is not logged.
- **`idempotentBatch` stores no result.** The SQS handler never reads one, so a `Response` or other non-JSON return value no longer fails the message after its side effect.
- **`complete` and `release` stay unconditional** (no owner check). With the expiry rule a takeover needs the Function timeout to have passed, and on Lambda the first execution has been stopped by then. `voke dev` and tests do not enforce the timeout; that is documented.
- **A route's default validation is its body.** Since route `request.headers` became a plain object (ADR 0018), hashing the whole request made a retry that differs only in a tracing header fail with `IDEMPOTENCY_PAYLOAD_MISMATCH`. `idempotent` recognises a route request by its `raw` `Request` and defaults `validate` to `request.body`; any other input still defaults to the whole input. `validate` overrides it.

Departures from Powertools for AWS Lambda (TypeScript): it writes no size check, rethrows a persistence error instead of the function's error when the delete fails, and wraps a failed update in its own error type like `IDEMPOTENCY_COMPLETE_FAILED` here. The expiry rule, the `RESULT_TOO_LARGE` status and keeping the handler's error are Voke's. Not compared: the value Powertools writes to its expiry attribute while in progress, and how its batch utility handles store errors.

Not covered: an owner token on the record, a retry loop for `complete`, returning the handler's result when the completion write fails, and per-message results in the batch form.
