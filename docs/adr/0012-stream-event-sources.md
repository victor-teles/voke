# Stream Event Sources: checkpoint batch results, trim-horizon start, retries until expiry

Voke supports Kinesis data streams and DynamoDB table streams as two AWS Event Sources, `kinesis({ stream, record, handler })` and `dynamodbStream({ table, item?, handler })` from `@voke/aws`, each referencing its resource by Voke resource key. They follow the SQS Event Source design (ADR "Add SQS Event Sources as a Function entrypoint") wherever the semantics allow: the handler receives a normalized batch (`batch.records`, `batch.ok()`, `batch.batchResult()`), a record that cannot be decoded or validated becomes a batch item failure by default (`invalidRecord: "include"` hands it to the handler), partial batch failure reporting is always on, and `functions.sendEvent` runs the same normalization locally with plain values. One stream or table per Function in v1.

Kinesis payloads are base64-decoded, read as UTF-8 and parsed as JSON before the `record` schema validates them. DynamoDB keys and images are converted from attribute-value JSON to plain values by an internal converter that mirrors `unmarshall` from `@aws-sdk/util-dynamodb`, so no dependency is added. It differs in one place: every `N` becomes a `number`, where `unmarshall` returns a `bigint` for integers beyond `Number.MAX_SAFE_INTEGER`, so an attribute never changes type between records; such integers lose precision.

The handler result is a new `StreamBatchResult`, not `SqsBatchResult`, although the wire shape is the same `{ batchItemFailures: [{ itemIdentifier }] }` and both use one internal builder. The contracts differ: SQS retries each failed message on its own, while for a stream Lambda checkpoints at the lowest reported sequence number and delivers that record and every record after it in the batch again. One name per concept keeps `SqsBatchResult` meaning independent messages and `StreamBatchResult` meaning a checkpoint.

New mappings start at `TRIM_HORIZON`. AWS documents that a `LATEST` mapping can miss records written while it is created or updated; trim horizon never skips them, and consumers must be idempotent anyway because delivery is at least once. `BisectBatchOnFunctionError` is on, so a handler that throws isolates the bad record by halving the batch.

`MaximumRetryAttempts` is not set, so Lambda retries a failing record until it expires from the stream. Without a failure destination, a capped mapping discards records after the last attempt, and a short downstream outage would exhaust a small cap within seconds. A stalled shard is visible through the iterator age and loses nothing until the retention period ends. Failure destinations belong to the deferred DLQ and redrive design; when it lands, this default is reconsidered together with it.

Only the consuming Function's role gets stream-read access, through an optional `roleStatements` capability on the internal Event Source adapter. Kinesis consumers get `DescribeStream`, `DescribeStreamSummary`, `GetRecords`, `GetShardIterator` and `ListShards` on the stream ARN; `ListStreams` (console only) and `SubscribeToShard` (enhanced fan-out) are left out. DynamoDB stream consumers get `DescribeStream`, `GetRecords` and `GetShardIterator` on the table's `StreamArn`, and `ListStreams` on `*`, matching `AWSLambdaDynamoDBExecutionRole`. Stream capacity, retention and view type stay on the resources: `kinesisStream()` (on demand unless `shardCount` is set) and `dynamodbTable({ stream })`.

Superseded in part by ADR 0020, "Failed events go to a dead-letter queue by default" (`0020-dead-letter-queues.md`).
