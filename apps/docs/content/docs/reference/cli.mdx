This page lists every `voke` command with its exact `--help` output, an example, and the guide that teaches it. Run commands from the project directory, where `voke.config.ts` lives.

```bash
voke --help
```

```txt
Voke v0.0.0

Usage: voke <command> [options]

Commands:
  voke build    Bundle the project's Functions through the Provider.
  voke create   Create a new API project and install its dependencies.
  voke deploy   Build and deploy a stage through the Provider.
  voke dev      Run the API locally with hot reload.
  voke doctor   Check the toolchain, the project and the Provider.
  voke local    Run the Provider's local environment. The Provider may accept more flags.
  voke migrate  Generate a Voke skeleton from a Serverless Framework service.
  voke remote   Generate Remote Function Registry modules from remotes.
  voke remove   Delete a deployed stage through the Provider.
  voke synth    Write the Provider's deployment template.

Run voke <command> --help for its flags. voke --version prints the version.
```

## Help, version and usage errors

`voke <command> --help` (or `-h`) and `voke help <command>` print the same usage and flags for one command. `voke --version` (or `-v`) prints the version:

```bash
voke help synth
voke --version
```

```txt
voke 0.0.0
```

Flags take a value as `--stage dev` or `--stage=dev`. An unknown flag, a flag without its value, or an unknown command is an error. The CLI prints the problem and the command's usage, then exits with code 1. For an unknown flag, it suggests the closest known flag:

```bash
voke synth --stag prod
```

```txt
Invalid CLI usage: Unknown flag --stag for "synth". Did you mean --stage?
Usage: voke synth [entrypoint] [out] [--config voke.config.ts] [--name api] [--stage local] [--region us-east-1]
```

An argument the command does not take, a short flag such as `-s`, and a flag with an empty value such as `--stage=` are usage errors too. Only `-h` and `-v` are short. The CLI names the flag you most likely meant:

```bash
voke deploy prod
```

```txt
Invalid CLI usage: Unexpected argument "prod" for "deploy". Did you mean --stage prod?
Usage: voke deploy [--stage dev] [--region us-east-1] [--config voke.config.ts] [--dry-run] [--accept-data-loss]
```

## Plugin commands

A [Plugin](/docs/guides/plugins) can add commands, run as `voke <plugin> <command>`. When `./voke.config.ts` loads, `voke --help` lists them under "Plugin commands:"; `voke <plugin>` lists one Plugin's commands, and `voke <plugin> <command> --help` prints a command's usage and flags. Every Plugin command accepts `--config`. Built-in commands always win, so no Plugin command can replace one.

## Project flags

Commands that read the project accept `--config`, `--entrypoint`, `--name`, `--region` and `--stage`. When `voke.config.ts` does not exist and you do not pass `--config`, Voke builds a config from these flags; the name falls back to the `package.json` name, then `api`. See [Config](/docs/reference/config) for every setting.

Relative paths, such as `--config` and the entrypoint, resolve against the working directory. This holds when `--config` points at a file in another directory too: the config's `entrypoint` still resolves against the directory you run `voke` in.

<Callout type="warn" title="Some commands need a Provider">
  The commands that need a Provider (`synth`, `build`, `deploy`, `remove`,
  `local`) fail with an example `provider: aws()` line when the config has none.
</Callout>

## build

```txt
Usage: voke build [entrypoint] [outdir]

Bundle the project's Functions through the Provider.

Flags:
  --config <value>      Config file. Default: voke.config.ts
  --entrypoint <value>  Project entrypoint. Default: ./src/index.ts
  --name <value>        Project name when there is no config file
  --region <value>      Region. Default: the config
  --stage <value>       Stage. Default: VOKE_STAGE, then the config
  --outdir <value>      Output directory. Default: ./dist
```

```bash
voke build
voke build ./src/index.ts ./dist
```

`voke build` bundles the entrypoint into one ESM bundle for the AWS Lambda Node.js runtime, with one generated handler per Function, and writes a `package.json` with `"type": "module"` next to it. Modules that match `build.external` stay out of the bundle; the default, `["@aws-sdk/*"]`, uses the AWS SDK that ships with the Lambda runtime. It prints `Built <outdir>`. `voke deploy` runs the build for you. See [Deploy](/docs/guides/deploy).

Give the entrypoint and the output directory as arguments or as `--entrypoint` and `--outdir`, not both.

## create

```txt
Usage: voke create <name> [directory]

Create a new API project and install its dependencies.

Flags:
  --force       Write into a non-empty directory, overwriting the starter files
  --no-install  Skip bun install
```

```bash
voke create hello-api
voke create @acme/orders ./orders-api --no-install
```

`voke create` writes an API project to `./<name>` (without the scope), or to `directory`, runs `bun install`, and prints the next steps. The `package.json` name is exactly `<name>`, scope included. A non-empty directory is refused unless you pass `--force`, which overwrites the starter files and keeps every other file. See [Getting started](/docs/getting-started).

## deploy

```txt
Usage: voke deploy [--stage dev] [--region us-east-1] [--config voke.config.ts] [--dry-run] [--accept-data-loss]

Build and deploy a stage through the Provider.

Flags:
  --config <value>      Config file. Default: voke.config.ts
  --entrypoint <value>  Project entrypoint. Default: ./src/index.ts
  --name <value>        Project name when there is no config file
  --region <value>      Region. Default: the config
  --stage <value>       Stage. Default: VOKE_STAGE, then the config
  --accept-data-loss    Apply changes that remove or replace a resource that holds data
  --dry-run             Preview the changes without applying them
```

```bash
voke deploy --stage dev
voke deploy --stage prod --dry-run
```

`voke deploy` builds the project, uploads the bundle, and deploys the stage through the Provider. It then prints the stack outputs (the API URL first) and writes them to `.voke/outputs/<stage>.json`. `--dry-run` previews the changes without applying them and writes no outputs file. A deploy that would remove or replace a table, a bucket or a secret stops before it changes anything and names each resource; `--accept-data-loss` applies it anyway and lists the resources it kept. The stage comes from `--stage`, then `VOKE_STAGE`, then the config. The stage `local` is refused unless `AWS_ENDPOINT_URL` or `VOKE_AWS_ENDPOINT_URL` is set. See [Deploy](/docs/guides/deploy).

## dev

```txt
Usage: voke dev [entrypoint] [--hostname localhost] [--port 3000]

Run the API locally with hot reload.

Flags:
  --config <value>      Config file. Default: voke.config.ts
  --entrypoint <value>  Project entrypoint. Default: ./src/index.ts
  --name <value>        Project name when there is no config file
  --region <value>      Region. Default: the config
  --stage <value>       Stage. Default: VOKE_STAGE, then the config
  --endpoint <value>    Local cloud endpoint for resource bindings
  --hostname <value>    Hostname. Default: localhost
  --port <value>        Port. Default: 3000
```

```bash
voke dev
PORT=4000 voke dev
```

`voke dev` runs `dev.entrypoint` with `bun --hot`, so the Gateway reloads when you save a file. The server listens on `PORT` (default 3000). It sets `environment`, `dev.environment`, the remote targets and the Local AWS Provider's environment. It runs without a Provider, and prints a note that one is missing. See [Getting started](/docs/getting-started) and [Local AWS](/docs/guides/local-aws).

Give the entrypoint as an argument or as `--entrypoint`, not both. `--port` must be a number from 1 to 65535.

<Callout type="warn" title="--port does not move the server">
  `--hostname` and `--port` only change the address Voke reports for the dev
  server (`VOKE_DEV_ORIGIN`, used by remote projects); they do not move the
  server, so set `PORT` to change the port.
</Callout>

## doctor

```txt
Usage: voke doctor [--config voke.config.ts]

Check the toolchain, the project and the Provider.

Flags:
  --config <value>  Config file. Default: voke.config.ts
```

```bash
voke doctor
```

`voke doctor` prints one `ok`, `warn` or `fail` row per check: the Bun version, the config, the entrypoint, the discovered Functions and routes, the Provider, and the Provider's own checks. For `aws()`, these are the credentials (with the account id and region) and the local container tool. It never prints credentials. It exits with code 1 when any row fails. See [Troubleshooting](/docs/guides/troubleshooting).

## local

```txt
Usage: voke local <start|stop|reset|bootstrap>

Run the Provider's local environment. The Provider may accept more flags.

Flags:
  --config <value>      Config file. Default: voke.config.ts
  --entrypoint <value>  Project entrypoint. Default: ./src/index.ts
  --name <value>        Project name when there is no config file
  --region <value>      Region. Default: the config
  --stage <value>       Stage. Default: VOKE_STAGE, then the config
```

```bash
voke local start
voke local bootstrap
```

`voke local` runs the workflow of the **Local AWS Provider** set in `aws({ local })`: the AWS Emulator by default, or Floci with `aws({ local: floci() })`. `start` starts it, `bootstrap` deploys the project's resources into it, `stop` stops it, and `reset` deletes its state. See [Local AWS](/docs/guides/local-aws).

`voke local` also accepts the flags that the Local AWS Provider declares. They do not appear in `--help`, and they go after the subcommand (`voke local start --rebuild`); the core flags above may come before it. With `aws()`, every Local AWS Provider accepts:

| Flag                 | Description                                                                 |
| -------------------- | --------------------------------------------------------------------------- |
| `--endpoint <value>` | Local AWS endpoint for `bootstrap`.                                         |
| `--template <value>` | Template written by `bootstrap`. Default: `.voke/local/cloudformation.json` |

The AWS Emulator also accepts:

| Flag        | Description                                       |
| ----------- | ------------------------------------------------- |
| `--rebuild` | Rebuild the AWS Emulator image even if it exists. |

Floci also accepts:

| Flag                 | Description                                                    |
| -------------------- | -------------------------------------------------------------- |
| `--compose <value>`  | Docker Compose file. Default: `.voke/local/docker-compose.yml` |
| `--data <value>`     | Floci data directory. Default: `.voke/local/data`              |
| `--hostname <value>` | Floci hostname.                                                |
| `--image <value>`    | Floci container image.                                         |
| `--port <value>`     | Floci port.                                                    |

```bash
voke local start --rebuild
```

## migrate

```txt
Usage: voke migrate serverless [serverless.yml] [--out ./voke-migration]

Generate a Voke skeleton from a Serverless Framework service.

Flags:
  --out <value>  Output directory. Default: ./voke-migration
```

```bash
voke migrate serverless
voke migrate serverless ./serverless.yml --out ./voke-migration
```

`voke migrate serverless` reads a Serverless Framework service and writes a Function-first Voke skeleton and a migration report to the output directory. It prints `Wrote migration skeleton to <directory>`. When the report has blocking tasks, it then prints `<n> blocking task(s) in <directory>/MIGRATION_REPORT.md:` and one `- <task>` line per task. The exit code stays `0`, because the affected routes are generated closed.

The command stops with a usage error, and writes no file, when it cannot read the file faithfully: a YAML syntax error, an empty file, a root that is not one mapping, a self-referencing alias, or a CloudFormation tag followed by a block value. See [Serverless migration](/docs/guides/serverless-migration).

## openapi

<Callout type="info" title="Plugin command">
  A command of the `openapi()` Plugin from `@voke/openapi`: it exists when
  `voke.config.ts` declares that Plugin.
</Callout>

```txt
Usage: voke openapi generate [--out openapi.json] [--server <url>]

Write the OpenAPI document of the project's HTTP API.

Flags:
  --out <value>     Output file. Default: openapi.json
  --server <value>  A server URL to list in the document
  --config <value>  Config file. Default: voke.config.ts
```

```bash
voke openapi generate
voke openapi generate --out ./dist/openapi.json --server https://api.example.com
```

`voke openapi generate` imports the entrypoint and writes the OpenAPI 3.1 document of every route as two-space JSON. It prints `Wrote <path> (<n> operations)`. See [OpenAPI and API reference](/docs/guides/openapi).

## remote

```txt
Usage: voke remote generate [name]

Generate Remote Function Registry modules from remotes.

Flags:
  --config <value>      Config file. Default: voke.config.ts
  --entrypoint <value>  Project entrypoint. Default: ./src/index.ts
  --name <value>        Project name when there is no config file
  --region <value>      Region. Default: the config
  --stage <value>       Stage. Default: VOKE_STAGE, then the config
```

```bash
voke remote generate
voke remote generate users
```

`voke remote generate` fetches the Function Contract metadata of each remote in `remotes` and writes one Remote Function Registry module per remote, to `remotes.<name>.out`. With a name, it generates only that remote. It prints `Wrote <path>` for each module. See [Remote Functions](/docs/guides/remote-functions).

## remove

```txt
Usage: voke remove [--stage dev] [--region us-east-1] [--config voke.config.ts] [--yes]

Delete a deployed stage through the Provider.

Flags:
  --config <value>      Config file. Default: voke.config.ts
  --entrypoint <value>  Project entrypoint. Default: ./src/index.ts
  --name <value>        Project name when there is no config file
  --region <value>      Region. Default: the config
  --stage <value>       Stage. Default: VOKE_STAGE, then the config
  --yes                 Skip the confirmation prompt
```

```bash
voke remove --stage dev
voke remove --stage preview --yes
```

`voke remove` deletes the stage's stack and its resources, except the tables, buckets and secrets that `aws({ retainData })` keeps: it lists each of them with its physical id and the command that deletes it. It asks you to type the stack name (`<name>-<stage>`) to confirm. `--yes` skips the prompt and is required outside a terminal, for example in CI. It prints `Removed <name>-<stage>`, or `Nothing to remove` when the stage does not exist. See [Deploy](/docs/guides/deploy).

## synth

```txt
Usage: voke synth [entrypoint] [out] [--config voke.config.ts] [--name api] [--stage local] [--region us-east-1]

Write the Provider's deployment template.

Flags:
  --config <value>      Config file. Default: voke.config.ts
  --entrypoint <value>  Project entrypoint. Default: ./src/index.ts
  --name <value>        Project name when there is no config file
  --region <value>      Region. Default: the config
  --stage <value>       Stage. Default: VOKE_STAGE, then the config
  --out <value>         Output file. Default: cloudFormation.out
```

```bash
voke synth
voke synth --stage prod --out ./dist/prod.json
```

`voke synth` imports the entrypoint, discovers the Functions, and writes the Provider's deployment template. With `aws()`, this is a CloudFormation template at `cloudFormation.out` (default `./dist/cloudformation.json`). It prints `Wrote template to <path> (<n> resources)`. It deploys nothing. See [Deploy](/docs/guides/deploy).

Give the entrypoint and the output file as arguments or as `--entrypoint` and `--out`, not both.
