After this page you can declare the AWS resources your project needs, link each one to the Functions that use it, read its deployed name or URL from a handler, and create AWS SDK clients that work both locally and on AWS. It also lists the access a link grants.

## Declare resources

Declare resources in `resources` in `voke.config.ts`, with the builders from
`@voke/aws/cloudformation`. The key of each entry (`usersTable` below) is the **resource key**: you
use it to link the resource to a Function, and Voke derives the CloudFormation logical id from it.

```ts title="voke.config.ts" twoslash
import { aws } from "@voke/aws";
import { dynamodbTable, s3Bucket, sqsQueue } from "@voke/aws/cloudformation";
import { defineConfig } from "voke";

export default defineConfig({
  name: "users",
  provider: aws(),
  resources: {
    usersTable: dynamodbTable({ partitionKey: "id" }),
    uploadsBucket: s3Bucket(),
    jobsQueue: sqsQueue(),
  },
});
```

`voke synth` and `voke deploy` add each resource to the stack, and `voke local bootstrap` creates them
in the Local AWS Provider. See [Local AWS](/docs/guides/local-aws).

## Builders

Each builder declares one AWS resource and exposes one binding attribute.

| Builder                          | AWS resource                  | Options                                                                                                                                                                               | Binding attribute |
| -------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| `dynamodbTable(options?)`        | `AWS::DynamoDB::Table`        | `partitionKey` (default `"id"`), `sortKey`. Both are string (`S`) keys. Billing is on demand (`PAY_PER_REQUEST`). `stream`, `ttlAttribute`.                                           | `name`            |
| `sqsQueue(options?)`             | `AWS::SQS::Queue`             | `visibilityTimeoutSeconds`. See [SQS events](/docs/guides/sqs-events#queue-visibility-timeout). `deadLetterQueue: false` (see [Dead-letter queues](/docs/guides/dead-letter-queues)). | `url`             |
| `kinesisStream(options?)`        | `AWS::Kinesis::Stream`        | `shardCount` (provisioned mode; on demand by default), `retentionHours`. See [Kinesis events](/docs/guides/kinesis-events).                                                           | `name`            |
| `snsTopic()`                     | `AWS::SNS::Topic`             | None. See [SNS events](/docs/guides/sns-events).                                                                                                                                      | `arn`             |
| `eventBus()`                     | `AWS::Events::EventBus`       | None. See [EventBridge events](/docs/guides/eventbridge-events).                                                                                                                      | `name`            |
| `s3Bucket()`                     | `AWS::S3::Bucket`             | None. See [S3 events](/docs/guides/s3-events).                                                                                                                                        | `name`            |
| `secret()`                       | `AWS::SecretsManager::Secret` | None. AWS generates the secret value.                                                                                                                                                 | `id`              |
| `ssmParameter({ value, type? })` | `AWS::SSM::Parameter`         | `value` (required), `type`: `"String"` (default) or `"StringList"`.                                                                                                                   | `name`            |

`dynamodbTable({ stream })` also turns on the table's stream, with a view type such as
`"NEW_AND_OLD_IMAGES"`, so a Function can consume it. See
[DynamoDB stream events](/docs/guides/dynamodb-stream-events).

`dynamodbTable({ ttlAttribute: "expiresAt" })` turns on time to live: DynamoDB deletes an item some
time after the epoch-seconds value in that attribute has passed. Deletion runs in the background,
usually within a few days, so reads can still return expired items. The attribute is not a key, so
it needs no declaration. The [idempotency Plugin](/docs/guides/idempotency) uses it for its table.

AWS generates the physical names. Your code never hard-codes a table name or a queue URL: a Function
links the resource and reads its binding.

<Callout type="info" title="Two functions are named secret">
  `secret` from `@voke/aws/cloudformation` declares a Secrets Manager resource.
  `secret` from `@voke/aws` is a different function that reads a secret at run
  time. To read the value of a declared `secret()` or `ssmParameter()`, use a
  [Runtime Variable](/docs/guides/runtime-variables) with `.fromResource(key)`.
</Callout>

## Data retention

A table, a bucket and a generated secret hold data that exists nowhere else, and a redeploy cannot
recreate it. Voke calls them **data-bearing resources** and keeps them by default, on every stage:
`dynamodbTable()`, `s3Bucket()` and `secret()` get `DeletionPolicy: Retain`,
`UpdateReplacePolicy: Retain` and the metadata entry `VokeRetain: true` in the template. When such a
resource leaves the stack, is replaced, or the stage is removed, CloudFormation leaves it in the
account instead of deleting it.

The other builders are not data-bearing. A queue and a stream carry records in transit for a bounded
time, and a retained one would have no consumer but still cost money. A topic and an event bus store
nothing, and a parameter's value is in your config.

To delete data-bearing resources with their stack, set `retainData` on the AWS Provider. It is
`true`, `false`, or a predicate that decides per resource with the resolved stage, including
`--stage`:

```ts title="voke.config.ts" twoslash
import { aws } from "@voke/aws";
import { dynamodbTable, s3Bucket } from "@voke/aws/cloudformation";
import { defineConfig } from "voke";

export default defineConfig({
  name: "users",
  // Keep data on prod only; every other stage deletes it with the stack.
  provider: aws({ retainData: ({ stage }) => stage === "prod" }),
  resources: {
    usersTable: dynamodbTable({ partitionKey: "id" }),
    cacheBucket: s3Bucket(),
  },
});
```

The predicate receives `{ key, stage, type }`: the resource key, the stage and the CloudFormation
type, so `({ key }) => key !== "cacheBucket"` keeps every data-bearing resource except one. Decide
retention here, not from `process.env.VOKE_STAGE` in the config: the config file does not see the
`--stage` flag.

The resource key, and a table's `partitionKey` and `sortKey`, identify the resource. Renaming the
key or changing a table's keys means a new, empty resource. `voke deploy` refuses such a change
until you pass `--accept-data-loss`. See
[Changes that remove or replace data](/docs/guides/deploy#changes-that-remove-or-replace-data).

Raw resource definitions in `resources` (objects with `cloudFormationType` instead of a builder)
pass through untouched: Voke adds no policy to them, whatever their type. `voke deploy` still
refuses to remove or replace one whose type is a table, a bucket or a secret.

CloudFormation applies the policy of the template that is already deployed. A stack deployed with an
earlier Voke version has no policy yet, so a resource you remove in the first deploy after the
upgrade is still deleted. Deploy once without removing anything to protect it.

## Read a resource from a Function

A Function lists the resources it uses in `resources`, by resource key. Each entry is a **Resource
Link**. The Function's handler then reads a linked resource's binding value with
`context.resource(key)`: a table name, a queue URL, a topic ARN, a secret id.

```ts twoslash
import { schema } from "@voke/schema";
import { fn } from "voke";

// ---cut---
const countUsers = fn({
  resources: ["usersTable"],
  output: schema.string(),
  handler: (_payload, context) => context.resource("usersTable"),
});
```

Every Function builder takes `resources`: `fn`, `http`, `requestAuthorizer`, `durable` and every
Event Source builder (`sqs`, `sns`, `eventBridge`, `schedule`, `kinesis`, `dynamodbStream`, `s3`).
The keys are typed from the Function's own list: with `resources: ["usersTable"]`,
`context.resource("jobsQueue")` does not compile, and a Function without `resources` cannot call
`context.resource` at all. That each key exists in `voke.config.ts` is checked when the model is
built: `voke dev`, `voke synth`, `voke build` and `voke deploy` fail with a `VokeConfigError` that
names the Function and the key, for example
`Function "countUsers" links resource "usrsTable", but no matching resource is defined.`

A link gives the Function two things, and no other Function gets them:

- the binding, an environment variable `VOKE_RESOURCE_<KEY>_<ATTRIBUTE>` with the resource key and
  the binding attribute in upper snake case (`usersTable` gets `VOKE_RESOURCE_USERS_TABLE_NAME`,
  `jobsQueue` gets `VOKE_RESOURCE_JOBS_QUEUE_URL`);
- the resource's statement in the Function's IAM role. See
  [Access a link grants](#access-a-link-grants).

`context.resource` checks the link every time it runs, in `voke dev`, in tests and on AWS, so a
missing link fails before you deploy. It throws `VokeResourceBindingError` (code
`RESOURCE_BINDING_ERROR`):

- `Function "<key>" does not link resource "<resource>". Add it to the Function: resources: ["<resource>"]`
  when the Function does not link the resource.
- `Missing resource binding: VOKE_RESOURCE_...` when the variable is unset or empty.

Read bindings through `context.resource`, not from `process.env`. `voke dev` runs every Function in
one process with every binding set, so a direct read passes locally and finds nothing once deployed.
Code that runs outside a handler takes the value as an argument.

Where the values come from:

- **Deployed**, CloudFormation sets them on each Lambda from the stack's resources, for the
  resources that Function links.
- **In `voke dev`**, Voke sets them from the resources in the Local AWS Provider. With the AWS
  Emulator, run `voke local bootstrap` first: Voke reads the names it recorded. See
  [Local AWS](/docs/guides/local-aws).
- **In tests**, set the variable yourself and compose the Gateway with the config,
  `voke(functions, { config })`. See [Testing](/docs/guides/testing).

## Create AWS SDK clients with `createAwsClientConfig()`

Pass `createAwsClientConfig()` from `@voke/aws` to every AWS SDK client you create, for example
`new DynamoDBClient(createAwsClientConfig())`. It returns `{ region, endpoint? }`:

- `region` is the first value set among the `region` option, `AWS_REGION` and `AWS_DEFAULT_REGION`.
  The default is `us-east-1`.
- `endpoint` is the `endpoint` option, then `VOKE_AWS_ENDPOINT_URL`, then `AWS_ENDPOINT_URL`. `voke dev`
  and local commands set these to the Local AWS Provider. A deployed Lambda has neither, so
  `endpoint` is left out and the SDK uses its default AWS endpoint.

<Callout type="warn" title="SQS calls can reach real AWS">
  Do not skip `createAwsClientConfig()` for SQS. SQS queue URLs carry the real AWS host
  (`https://sqs.<region>.amazonaws.com/...`). An SQS client without an explicit endpoint sends a
  call for that queue URL to that host, which is real AWS, even while you run locally.
</Callout>

You can pass overrides: `createAwsClientConfig({ region: "eu-west-1" })`.

## Example: a DynamoDB table read by a route

The table is declared in `voke.config.ts`, the Function links it, and its route reads the table name
and the client config:

```ts twoslash
// @filename: voke.config.ts
import { aws } from "@voke/aws";
import { dynamodbTable } from "@voke/aws/cloudformation";
import { defineConfig } from "voke";

export default defineConfig({
  name: "users",
  provider: aws(),
  resources: {
    usersTable: dynamodbTable({ partitionKey: "id" }),
  },
});

// @filename: src/index.ts
import { DynamoDBClient, GetItemCommand } from "@aws-sdk/client-dynamodb";
import { createAwsClientConfig } from "@voke/aws";
import { schema } from "@voke/schema";
import { createFunctions, http, voke } from "voke";

import config from "../voke.config";

const functions = createFunctions({
  http: http({
    resources: ["usersTable"],
    routes: (route) => [
      route.get("/users/:id", {
        params: schema.object({ id: schema.string() }),
        handler: async (request, context) => {
          const client = new DynamoDBClient(createAwsClientConfig());
          const { Item } = await client.send(
            new GetItemCommand({
              Key: { id: { S: request.params.id } },
              TableName: context.resource("usersTable"),
            })
          );

          return { found: Item !== undefined, id: request.params.id };
        },
      }),
    ],
  }),
});

export default voke(functions, { config });
```

The handler's `context` is typed with the Function's links when routes are written with the callback
form, `routes: (route) => [...]`. With the shared `route` import, `context.resource` accepts any
key and the link is checked at run time only.

Install the AWS SDK clients you use (`bun add @aws-sdk/client-dynamodb`). `voke build` leaves
`@aws-sdk/*` out of the bundle by default, because the Lambda Node.js runtime provides it.

## Access a link grants

Voke synthesizes one IAM role per Function. Each role gets the AWS managed policy
`AWSLambdaBasicExecutionRole` (logs), plus one policy, `VokeResourceAccess`, with one statement for
each resource the Function links:

| Builder           | Actions                                                                                                                            | Resource                              |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| `dynamodbTable()` | `dynamodb:GetItem`, `PutItem`, `UpdateItem`, `DeleteItem`, `Query`, `Scan`, `BatchGetItem`, `BatchWriteItem`, `ConditionCheckItem` | The table ARN.                        |
| `sqsQueue()`      | `sqs:SendMessage`, `ReceiveMessage`, `DeleteMessage`, `GetQueueAttributes`                                                         | The queue ARN.                        |
| `kinesisStream()` | `kinesis:PutRecord`, `kinesis:PutRecords`                                                                                          | The stream ARN.                       |
| `snsTopic()`      | `sns:Publish`                                                                                                                      | The topic ARN.                        |
| `eventBus()`      | `events:PutEvents`                                                                                                                 | The event bus ARN.                    |
| `s3Bucket()`      | `s3:ListBucket` on the bucket; `s3:GetObject`, `PutObject`, `DeleteObject` on its objects                                          | The bucket ARN, and `<bucket ARN>/*`. |
| `secret()`        | `secretsmanager:GetSecretValue`                                                                                                    | The secret ARN.                       |
| `ssmParameter()`  | `ssm:GetParameter`, `ssm:GetParameters`                                                                                            | The parameter ARN.                    |

A DynamoDB transaction needs no action of its own: each item in it is authorized by its item action,
and a condition check by `dynamodb:ConditionCheckItem`. A link grants the whole list; read-only links
are not available yet.

Access is scoped to each resource's ARN, never to `*`, and to the Functions that link the resource.
The rules:

- **A Function that does not link a resource** gets neither its statement nor its binding. Deployed,
  a read fails with `AccessDenied` or a missing binding.
- **An `http()` Function is one Function**: its links cover all its routes. To isolate a route, put
  it in its own `http()` Function.
- **An Event Source** gives its Function what the trigger needs on the source resource, and nothing
  else: an SQS consumer gets `sqs:ReceiveMessage`, `DeleteMessage` and `GetQueueAttributes` on its
  queue, and a [Kinesis](/docs/guides/kinesis-events#what-gets-deployed) or
  [DynamoDB stream](/docs/guides/dynamodb-stream-events#what-gets-deployed) consumer gets read access
  to the stream. SNS, EventBridge, S3 and schedule triggers need nothing on the role. A handler that
  also sends to its queue, reads the uploaded object or writes the table links that resource.
- **A [Runtime Variable](/docs/guides/runtime-variables#iam-permissions)** built with
  `.fromResource(key)` gives its Function the read permission and the binding it needs without a
  link. It does not make `context.resource(key)` available.
- **A resource a [Plugin](/docs/guides/plugins) contributes** is linked like any other, for example
  the idempotency table.
- **`awsPolicy()` statements from a Plugin** reach every Function role, because a Plugin's Function
  Wrap runs around every Function.
- **An in-process invocation** (`functions.invoke` that runs the other Function's handler in the
  same process) runs with the caller's role and environment. A read there must be linked by both the
  running Function and the Function that was entered first; otherwise it throws
  `Function "<key>" reads resource "<resource>" while running in-process inside Function "<entry>", which does not link it.`
  An invocation that leaves the process, such as starting a Durable Function, starts with its own
  links.
