---
title: Calling other projects
description: Call the Functions of another Voke Project during local development through a generated Remote Function Registry.
---

After reading this page you can call a Function of one Voke Project from another Voke Project while
both run under `voke dev`, with a generated client that you check into the calling project.

A **Remote Function Registry** is that generated client. The project that exposes Functions is the
_provider project_; the project that calls them is the _consumer project_. The consumer never imports
the provider's code. It uses only the provider's contract metadata, so the two projects can live in
different repositories.

<Callout type="warn" title="Local development only">
  Remote Function Registries work only between local `voke dev` servers in this
  version. A deployed Lambda cannot call another project through them: the
  endpoints exist only under `voke dev`, and only `voke dev` gives the consumer
  the provider's address. Deployed cross-project calls are not built yet.
</Callout>

## How it works

<Steps>
<Step>

### The provider project runs `voke dev`

Under `voke dev`, the Gateway of every project serves two extra endpoints:

- `GET /_voke/contract` returns the project's **contract metadata**: the project name, the input and
  output schema of each invokable Function, and a fingerprint of all of it.
- `POST /_voke/functions/<functionKey>/invoke` runs one invokable Function and returns its result.

These endpoints are separate from your HTTP routes. A Function with no route can still be called
from another project. Only invokable Functions (`fn()`) are included. `http()` and `sqs()` Functions
are not.

</Step>
<Step>

### The consumer project declares the remote

The consumer lists the provider in `remotes` in its `voke.config.ts`.

</Step>
<Step>

### `voke remote generate` writes the client

The command fetches the contract metadata and writes a TypeScript module that you check in.

</Step>
<Step>

### The consumer calls Functions by key

Code in the consumer imports the generated registry and calls `invoke(functionKey, payload)`.

</Step>
</Steps>

## Expose Functions from the provider project

A provider project needs nothing special. Its invokable Functions are exposed under `voke dev`.
The project `name` in its config is the name consumers use:

```ts twoslash
// @filename: voke.config.ts
import { aws } from "@vokejs/aws";
import { defineConfig } from "voke";

export default defineConfig({ name: "users", provider: aws() });

// @filename: src/index.ts
import { schema } from "@vokejs/schema";
import { createFunctions, fn, voke } from "voke";

import config from "../voke.config";

const functions = createFunctions({
  getUser: fn({
    input: schema.object({ id: schema.string() }),
    output: schema.object({ id: schema.string(), name: schema.string() }),
    handler: (payload) => ({ id: payload.id, name: "Ada" }),
  }),
});

export default voke(functions, { config });
```

Run it on a port that the consumer does not use:

```bash
PORT=3001 voke dev
```

## Declare the remote in the consumer project

Add the provider to `remotes`. The key must be the provider's project `name`:

```ts title="voke.config.ts" twoslash
import { aws } from "@vokejs/aws";
import { defineConfig } from "voke";

export default defineConfig({
  name: "wallet",
  provider: aws(),
  remotes: {
    users: {
      targets: {
        local: "http://localhost:3001",
      },
    },
  },
});
```

| Field      | Required | Meaning                                                                                             |
| ---------- | -------- | --------------------------------------------------------------------------------------------------- |
| `targets`  | Yes      | The provider's origin per stage. A target is a URL, or `{ origin, contract? }`.                     |
| `out`      | No       | Where `voke remote generate` writes the module. Default: `src/voke/remotes/<name>.ts`.              |
| `contract` | No       | The URL of the contract metadata. Default: the target's `contract`, then `<origin>/_voke/contract`. |

Voke picks the target for the current stage, and falls back to `targets.local` when there is no
target for that stage. The default stage is `local`. If neither exists, loading the config fails
with a `VokeConfigError` that names the missing `remotes.<name>.targets.<stage>`.

## Generate the client

With the provider's `voke dev` running, run this in the consumer project:

```bash
voke remote generate users   # one remote
voke remote generate         # every remote in remotes
```

The command writes the module to `out` and creates its folder if needed. Commit the file. It starts
with `// @generated by Voke. Do not edit manually.` and exports one registry, named after the remote,
made with `createRemoteFunctions` from `@vokejs/remote`. The consumer project needs `@vokejs/remote` as a
dependency.

## Call a remote Function

Import the registry and call `invoke(functionKey, payload)`. It returns a promise of the result:

```ts twoslash
// @filename: src/voke/remotes/users.ts
// @generated by Voke. Do not edit manually.
import { createRemoteFunctions } from "@vokejs/remote";

export const users = createRemoteFunctions("users", {
  functions: {
    getUser: {
      input: {
        type: "object",
        properties: { id: { type: "string" } },
        required: ["id"],
      },
      output: {
        type: "object",
        properties: { id: { type: "string" }, name: { type: "string" } },
        required: ["id", "name"],
      },
    },
  },
  project: "users",
  version: 1,
  fingerprint: "sha256:4f1c...",
} as const);

// @filename: src/index.ts
import { users } from "./voke/remotes/users";

// ---cut---
const user = await users.invoke("getUser", { id: "usr_1" });

console.info(user.name);
```

Run the consumer with `voke dev`. `invoke()` sends the call to the provider's origin, which
`voke dev` passes to the consumer as `VOKE_REMOTE_<NAME>_ORIGIN` (`VOKE_REMOTE_USERS_ORIGIN` here).
Outside `voke dev`, set that variable yourself, or `invoke()` throws a `VokeConfigError`:
`Remote Function Registry "users" has no runtime target`.

Before the request, `invoke()` checks the payload against the input schema in the contract. After
the response, it checks the result against the output schema. A failure throws an `InvokeError` with
code `INVALID_PAYLOAD` or `INVALID_RESULT`. The provider also validates the payload with its own
Function Contract, as for any invocation.

### Call options

`invoke()` takes a third argument with these options:

| Option      | Meaning                                                                                                                                      |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `trace`     | Trace values, such as `requestId`, that the provider's handler reads in `context.trace`.                                                     |
| `timeoutMs` | The time limit of each attempt, in milliseconds. When it passes, the request is cancelled. The provider project's handler may keep running.  |
| `retries`   | Extra attempts after a timeout, a request that failed or a 5xx answer. Voke never repeats a call after a 4xx answer, such as contract drift. |

`mode`, `executionName`, `runtime`, `transport` and `onAsyncError` are not accepted: they do not
compile, and at run time `invoke()` rejects with `INVALID_OPTIONS` before any request.

```ts twoslash
// @filename: src/voke/remotes/users.ts
// @generated by Voke. Do not edit manually.
import { createRemoteFunctions } from "@vokejs/remote";

export const users = createRemoteFunctions("users", {
  functions: {
    getUser: {
      input: {
        type: "object",
        properties: { id: { type: "string" } },
        required: ["id"],
      },
      output: {
        type: "object",
        properties: { id: { type: "string" }, name: { type: "string" } },
        required: ["id", "name"],
      },
    },
  },
  project: "users",
  version: 1,
  fingerprint: "sha256:4f1c...",
} as const);

// @filename: src/index.ts
import { users } from "./voke/remotes/users";

// ---cut---
const user = await users.invoke(
  "getUser",
  { id: "usr_1" },
  { retries: 1, timeoutMs: 2000 }
);

console.info(user.name);
```

### Types come from JSON Schema

The payload and result types, and the checks above, come from the JSON Schema in the contract
metadata. Voke reads each schema's JSON Schema through [Standard JSON Schema](https://standardschema.dev/json-schema):
the input side for `input` and the output side for `output`. `@vokejs/schema` and Zod schemas
implement it, so their contract entries are typed. A schema without it can carry a hand-written
`jsonSchema` property instead.

The contract keeps a subset of JSON Schema: `type`, `properties`, `required`, `items`,
`additionalProperties`, `const` and `enum`. Voke drops other keywords, such as `minLength`. A part
of a schema that the subset cannot express (a union, `anyOf`, `oneOf`, `allOf`, `not`, `$ref`, or a
`type` list such as a nullable field) becomes `true`: any value is accepted there and its type is
`unknown`. A schema with no JSON Schema at all, such as a Zod date, also becomes `true`. The
provider's own validation still runs in every case.

<Callout type="warn" title="Regenerate existing clients once">
  Contracts generated before Voke read Standard JSON Schema have `true` entries
  for `@vokejs/schema` and Zod schemas, so their fingerprints changed once. Run
  `voke remote generate` once in every consumer and commit the generated
  modules; until then, calls fail with contract drift.
</Callout>

## Contract drift

The generated module contains the contract's fingerprint, and every call sends it. When the provider's
contract has changed since you generated the module, the provider rejects the call with HTTP 409 and
`invoke()` throws an `InvokeError` with this message:

```txt
Remote Function contract drift for "users". Run `voke remote generate users`.
```

Run the command, review the diff of the generated file, and commit it.

A failed call always rejects with an `InvokeError`. Branch on its `code`. `statusCode` is set
whenever the provider project answered, so detect contract drift with `error.statusCode === 409`.

| Situation                                                                     | `InvokeError` code | `statusCode` |
| ----------------------------------------------------------------------------- | ------------------ | ------------ |
| The Function key is not in the generated module                               | `MISSING_FUNCTION` | none         |
| An option other than `trace`, `timeoutMs` and `retries`, or an invalid value  | `INVALID_OPTIONS`  | none         |
| The payload does not match the contract's input schema                        | `INVALID_PAYLOAD`  | none         |
| The request fails, for example nothing listens on the origin (`cause` is set) | `TRANSPORT_FAILED` | none         |
| An attempt takes longer than `timeoutMs`                                      | `TIMEOUT`          | none         |
| The provider has no invokable Function with that key (HTTP 404)               | `MISSING_FUNCTION` | 404          |
| Contract drift (HTTP 409), or any other error status from the provider        | `TRANSPORT_FAILED` | the status   |
| The provider answers 2xx without a Voke data envelope, such as an HTML page   | `TRANSPORT_FAILED` | the status   |
| The result does not match the contract's output schema                        | `INVALID_RESULT`   | none         |

For an error status, the message is the provider's error message, or
`Remote Function invocation failed with HTTP <status>` when the answer has none. Without a runtime
target, `invoke()` throws a `VokeConfigError` instead (see [Call a remote Function](#call-a-remote-function)).
