---
title: Migrate from Serverless Framework
description: Generate a Voke project skeleton and a migration report from a serverless.yml file, then move your functions over one at a time.
---

After this page you can turn a Serverless Framework service into a Voke project skeleton, read the migration report, and move the service to Voke one function at a time.

```bash
voke migrate serverless ./serverless.yml --out ./voke-migration
```

Both arguments are optional. The defaults are `./serverless.yml` and `./voke-migration`. The command prints `Wrote migration skeleton to ./voke-migration`.

## What the migrator reads

The migrator reads the service name, provider settings (stage, region, runtime, environment, IAM statements), functions and their events, native CloudFormation resources under `resources.Resources`, package patterns, and plugins.

<Callout type="warn" title="Limits of the YAML parser">
  Its YAML parser is small and has no dependencies. It covers the common
  Serverless Framework shapes: nested maps, lists, and scalars. Treat YAML
  anchors, custom tags, and plugin-specific `custom` settings as manual work.
</Callout>

## What it generates

    <File name="SERVERLESS_COMPATIBILITY.md" />
    <Folder name="src" defaultOpen>
      <File name="index.ts" />
      <Folder name="routes" defaultOpen>
        <File name="get-user.ts" />
      </Folder>
      <Folder name="functions" defaultOpen>
        <File name="index.ts" />
        <File name="nightly.ts" />
      </Folder>
    </Folder>
  </Folder>
</Files>

- `voke.config.ts`: the project name, the `aws()` Provider, stage, region, top-level `environment`, and top-level `resources`. It does not list Functions.
- `src/index.ts`: the project entrypoint. It builds the Function Registry with `createFunctions(...)`, mounts the routes, and exports the Gateway with `voke(functions, { config })`.
- `src/routes/*.ts`: Route Builder skeletons for `httpApi` and `http` (REST API) events. Path parameters such as `{id}` become `:id`.
- `src/functions/*.ts`: SQS Event Source Functions and EventBridge worker skeletons, with `src/functions/index.ts` as their Function Registry.
- `package.json` with the `build`, `clean`, `dev`, `synth`, `test`, and `typecheck` scripts, and `tsconfig.json`.
- `MIGRATION_REPORT.md` and `SERVERLESS_COMPATIBILITY.md`, described below.

`voke build` generates the Lambda handler of every Function from the entrypoint, so the Serverless `handler` paths are not carried over. Each skeleton keeps the original handler path in a comment or in its placeholder response.

### The generated config

For this `serverless.yml`:

```yaml title="serverless.yml"
service: users-api

provider:
  name: aws
  runtime: nodejs22.x
  stage: dev
  region: us-east-1
  environment:
    TABLE_NAME: users

functions:
  getUser:
    handler: src/handlers/get-user.handler
    events:
      - httpApi:
          method: GET
          path: /users/{id}
  nightly:
    handler: src/handlers/nightly.handler
    runtime: nodejs24.x
    events:
      - eventBridge:
          schedule: rate(1 day)
```

the migrator writes this `voke.config.ts`:

```ts title="voke.config.ts" twoslash
import { aws } from "@voke/aws";
import { defineConfig } from "voke";

export default defineConfig({
  name: "users-api",
  provider: aws({ lambda: { runtime: "nodejs22.x" } }),
  stage: "dev",
  region: "us-east-1",
  entrypoint: "./src/index.ts",
  environment: {
    TABLE_NAME: "users",
  },
});
```

A `provider.runtime` of `nodejs22.x` or `nodejs24.x` becomes `aws({ lambda: { runtime } })`. See [Functions](/docs/guides/functions) for Lambda settings.

<Callout type="warn" title="Other runtimes are dropped">
  Other runtimes, such as `nodejs20.x`, are dropped, and the Functions use the
  default runtime, `nodejs22.x`.
</Callout>

### A generated Function

A function with its own supported `runtime` gets an `awsLambda()` record in `synthesis.provider`. This is the generated EventBridge worker skeleton:

```txt title="src/functions/nightly.ts"
import { awsLambda } from "@voke/aws";
import { fn } from "voke";
import type { StandardSchemaV1 } from "voke";

const outputSchema: StandardSchemaV1<unknown, unknown> = {
  "~standard": {
    validate: (value: unknown) => ({ value }),
    vendor: "voke-migration",
    version: 1,
  },
};

// Original Serverless handler: src/handlers/nightly.handler
export const nightly = fn({
  name: "nightly",
  synthesis: {
    provider: awsLambda({ runtime: "nodejs24.x" }),
  },
  handler: async (payload: unknown) => {
    return {
      data: {
        eventTypes: ["eventBridge"],
        functionName: "nightly",
        migrated: true,
        originalHandler: "src/handlers/nightly.handler",
        payload,
      },
    };
  },
  output: outputSchema,
});
```

The skeleton accepts any value. Replace `outputSchema` with a real schema from `@voke/schema` and move your handler logic into `handler`. See [Schemas](/docs/guides/schemas).

### SQS events

An `sqs` event becomes an SQS Event Source Function, `sqs({ message, queue, handler })` from `@voke/aws`, when its queue resolves to an `AWS::SQS::Queue` resource that the migrator generated with `sqsQueue()` (for example `arn: { Fn::GetAtt: [OrdersQueue, Arn] }`). Batch settings such as `batchSize` carry over. Other `sqs` events get a plain Function skeleton and a manual task in the report. See [SQS events](/docs/guides/sqs-events).

### Resources

Native CloudFormation resources become top-level `resources` in `voke.config.ts` when Voke has a safe helper:

| CloudFormation type           | Generated helper         |
| ----------------------------- | ------------------------ |
| `AWS::DynamoDB::Table`        | `dynamodbTable({ ... })` |
| `AWS::SSM::Parameter`         | `ssmParameter({ ... })`  |
| `AWS::SQS::Queue`             | `sqsQueue()`             |
| `AWS::SNS::Topic`             | `snsTopic()`             |
| `AWS::S3::Bucket`             | `s3Bucket()`             |
| `AWS::Events::EventBus`       | `eventBus()`             |
| `AWS::SecretsManager::Secret` | `secret()`               |

The helpers come from `@voke/aws/cloudformation`. A queue, topic, bucket, event bus, or secret with any `Properties`, and every other resource type, is left out and reported as manual work with its type. See [Resources](/docs/guides/resources).

## Read the reports

`MIGRATION_REPORT.md` has these sections:

- **Summary**: counts of generated files, converted behavior, manual tasks, and unknown fields.
- **Generated files**: each path, its purpose, and a confidence level.
- **Converted behavior**: what the migrator mapped, by area, with the file it wrote.
- **Manual work by risk**: tasks grouped as high, medium, and low risk, each with an area, a reason, and a confidence level.
- **Plugin notes**, **Unknown fields**, **Compatibility projections** (supported features, unsupported features, manual steps), and the **Function inventory** and **Event inventory** of the service.

Confidence is `high`, `medium`, or `low`. `high` marks safe config conversions, and `medium` marks starter skeletons that need review. Areas are `routing`, `events`, `resources`, `iam`, `build`, `plugins`, and `unknown-fields`. When Voke knows why it cannot generate something, the task gives the reason, for example:

```txt
CloudFormation resource AuditLog (AWS::Logs::LogGroup) requires manual migration because Voke cannot safely generate an equivalent config helper.
```

Known plugins get a status and a note. For example, `serverless-offline` is reported as covered by `voke dev` and `voke local start`, and bundler plugins such as `serverless-esbuild` map to `voke build`, which bundles with Bun.

## Compatibility matrix

`SERVERLESS_COMPATIBILITY.md` lists every pattern with a status for your service (`Not present` when the service does not use it), a confidence level, the generated output, and the manual work.

| Serverless Framework pattern             | Status when present                                                              | Voke output                                 |
| ---------------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------- |
| `service`                                | Supported                                                                        | Project name in `voke.config.ts`            |
| `provider.stage`, `provider.region`      | Supported                                                                        | `stage` and `region` in `voke.config.ts`    |
| `provider.environment`                   | Supported                                                                        | Top-level `environment` in `voke.config.ts` |
| `provider.iamRoleStatements`             | Reported                                                                         | Manual IAM review task                      |
| `package.patterns`                       | Reported                                                                         | Manual build review task                    |
| `functions.*.events[].httpApi`           | Supported                                                                        | Route Builder skeleton                      |
| `functions.*.events[].http`              | Supported                                                                        | Route Builder skeleton                      |
| `functions.*.events[].sqs`               | Supported when the queue maps to a generated `sqsQueue()`, otherwise manual work | SQS Event Source Function                   |
| `functions.*.events[].eventBridge`       | Supported skeleton                                                               | Function skeleton                           |
| Native CloudFormation resources          | Supported skeleton                                                               | Top-level `resources` in `voke.config.ts`   |
| `sns`, `s3`, `schedule`, `stream` events | Inventory only                                                                   | Manual task in the report                   |
| `plugins`                                | Reported                                                                         | Per-plugin notes                            |

For an `sns` or `schedule` event, the report's manual task tells you to rewrite the function with
[`sns()`](/docs/guides/sns-events) or [`schedule()`](/docs/guides/scheduled-functions) from `@voke/aws`.

## Migrate incrementally

Move one function at a time, and keep the Serverless Framework service running until each one is verified.

<Steps>
<Step>

### Generate the skeleton

Run `voke migrate serverless` into a new directory, then run `bun install` there.

</Step>
<Step>

### Read the report

Start with the high-risk tasks in `MIGRATION_REPORT.md`, then the unsupported features.

</Step>
<Step>

### Port one route or worker

Pick one generated route or worker. Move the real handler logic into it, and replace the placeholder schemas with real ones. Replace unsupported events and plugins with explicit Voke code.

</Step>
<Step>

### Check and review

```bash
bun test
bun run typecheck
voke synth
```

Review the CloudFormation template that `voke synth` writes, then [deploy](/docs/guides/deploy) a stage.

</Step>
<Step>

### Move the traffic

Route traffic for that path or event to Voke. Remove the matching Serverless Framework function only after the Voke version is verified, then repeat with the next one.

</Step>
</Steps>
