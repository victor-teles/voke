## Function

A **Function** is a named serverless compute unit in a Voke Project. It can be invokable, route-backed, or event-source backed.

Use `fn()` for invokable Functions and `createFunctions()` for the project registry:

```ts
import { createFunctions, fn } from "voke";
import type { StandardSchemaV1 } from "voke";

const userInput: StandardSchemaV1<{ id: string }, { id: string }> = {
  "~standard": {
    validate: (value) => ({ data: value, success: true }),
    vendor: "example",
    version: 1,
  },
};

const getUser = fn({
  name: "getUser",
  input: userInput,
  output: userInput,
  handler: async (payload) => ({ id: payload.id }),
});

const functions = createFunctions({ getUser });

const user = await functions.invoke("getUser", { id: "usr_1" });
```

## Runtime Variables

Runtime Variables are per-Function implementation dependencies for values loaded at runtime. They do not change a Function Contract, and they are not exposed to generated remote clients.

Use provider-specific builders for app code. The first-party AWS builders live on `voke/aws`:

```ts
import { createFunctions, fn, voke } from "voke";
import { parameter, secret } from "voke/aws";

export const functions = createFunctions({
  checkout: fn({
    input: checkoutInput,
    output: checkoutOutput,
    variables: {
      flags: parameter("/prod/checkout/flags", { decrypt: false }),
      stripeKey: secret("/prod/stripe/key", {
        cache: { ttlSeconds: 60 },
        load: "beforeHandler",
      }),
    },
    handler: async (payload, context) => {
      const stripeKey = await context.variables.stripeKey.text();
      const flags = await context.variables.flags.json(flagsSchema);

      return checkout(payload, { flags, stripeKey });
    },
  }),
});

export const gateway = voke(functions, {
  variables: {
    overrides: {
      defaults: {
        flags: '{"enabled":true}',
      },
      functions: {
        checkout: {
          stripeKey: "sk_test_local",
        },
      },
    },
  },
});
```

Direct `secret(...)` and `parameter(...)` calls reference external AWS names or ARNs. Use `.fromResource(...)` for Voke-managed CloudFormation resource keys:

```ts
import { parameter, secret } from "voke/aws";

const variables = {
  publicConfig: parameter.fromResource("publicConfig"),
  signingSecret: secret.fromResource("signingSecret"),
};
```

Runtime Variables are required by default. Add `{ optional: true }` when absence is allowed. `text()` and `json(schema?)` return `undefined` for missing optional values, but invalid JSON, schema failures, AWS access failures, and provider failures still throw `VokeRuntimeVariableError`.

Values cache by warm Function runtime and Runtime Variable key. Use `cache: false` to reload after each completed read, `cache: { ttlSeconds }` for time-based reuse, and `await context.variables.key.refresh()` to rerun overrides, environment fallback, and provider loading.

Local and test resolution checks Function-scoped overrides, project defaults, `VOKE_VARIABLE_<FUNCTION>_<KEY>`, `VOKE_VARIABLE_<KEY>`, then the provider. Override values are strings so `text()` and `json(schema?)` behave the same across overrides, environment fallback, and providers.

Provider authors can use `voke/variables` to create provider objects and provider-specific builders. Providers are registered at the Gateway/test/runtime boundary, and unknown third-party providers fail before handler execution when Voke has enough context.

## Remote Function Registries

Use a **Remote Function Registry** when one Voke Project needs to invoke Functions exposed by another Voke Project during local development.

Provider project:

```ts
import { createFunctions, fn, voke } from "voke";

export const functions = createFunctions({
  getUser: fn({
    name: "getUser",
    input: userInput,
    output: userOutput,
    handler: async (payload) => ({ id: payload.id, name: "Victor" }),
  }),
});

export const gateway = voke(functions, { config: { name: "users" } });
```

Consumer config:

```ts
import { defineConfig } from "voke";

export default defineConfig({
  name: "wallet",
  remotes: {
    users: {
      targets: {
        local: "http://localhost:3001",
      },
    },
  },
});
```

Generate the checked-in remote module:

```bash
voke remote generate users
```

Then invoke by Function key from the generated registry:

```ts
import { users } from "./voke/remotes/users";

const user = await users.invoke("getUser", { id: "usr_1" });
```

During `voke dev`, the provider exposes Voke-owned contract metadata at `/_voke/contract` and a reserved internal Function invoke endpoint. Internal Functions do not need public HTTP routes to be invoked by another local Voke Project.

## Registry identity

The Function Registry key is the stable project identity used for type-safe invocation. The optional `name` field on a Function is a deployed Lambda name override, not the local registry key.

```ts
const functions = createFunctions({
  getUser: fn({
    name: "production-user-reader",
    input: userInput,
    output: userInput,
    handler: async (payload) => payload,
  }),
});

await functions.invoke("getUser", { id: "usr_1" });
```

## Route-backed Functions

Route-backed Functions expose HTTP routes through the Gateway. The Route Builder keeps HTTP route declarations in the first-party Voke API:

```ts
import { createFunctions, http, route, voke } from "voke";

export const functions = createFunctions({
  http: http({
    routes: [
      route.get("/health", {
        handler: () => ({ ok: true }),
      }),
    ],
  }),
});

export const gateway = voke(functions);
```

## HTTP API Authorizers

Use an Authorizer Registry when route-backed Functions should be protected by AWS API Gateway HTTP API v2 authorizers:

```ts
import {
  createAuthorizers,
  jwtAuthorizer,
  lambdaAuthorizer,
  requestAuthorizer,
} from "@voke/aws";
import { createFunctions, http, route, voke } from "voke";

const authorizers = createAuthorizers({
  session: lambdaAuthorizer({ function: "authorizeSession" }),
  userJwt: jwtAuthorizer({
    audience: "users-api",
    issuer: "https://auth.example.com",
  }),
});

export const functions = createFunctions({
  authorizeSession: requestAuthorizer({
    handler: async (request) => ({
      authorized: request.headers.get("authorization") === "Bearer dev",
      context: { userId: "usr_1" },
    }),
  }),
  users: http({
    authorizer: "userJwt",
    authorizers,
    routes: [
      route.get("/me", {
        authorizer: "session",
        handler: (request) => ({ userId: request.auth.context.userId }),
      }),
      route.get("/health", {
        authorizer: "none",
        handler: () => ({ ok: true }),
      }),
    ],
  }),
});

export const gateway = voke(functions);
```

The `http(...)` default authorizer protects routes that do not specify an override. A route uses `authorizer: "none"` when it is intentionally public. Merely defining an Authorizer Registry does not protect routes until the default or a route override references an authorizer.

JWT and Lambda Authorizers default to the `Authorization` header. Lambda Authorizers can set `cacheTtlSeconds`, which defaults to `0`, and can target a local Request Authorizer Function, an external deployed Lambda name, or a Lambda ARN. ARN targets are preferred for external authorizers because account and region ownership are explicit. External targets are bring-your-own-permission in v1.

## SQS Event Source Functions

SQS Event Source Functions are invoked by a queue and tested through `functions.sendEvent(...)`. They do not declare an output schema because Voke owns the SQS batch result contract:

```ts
import { createFunctions } from "voke";
import { sqs } from "@voke/aws";
import type { StandardSchemaV1 } from "voke";

const orderMessageSchema: StandardSchemaV1<
  { orderId: string },
  { orderId: string }
> = {
  "~standard": {
    validate: (value) => ({
      data: value as { orderId: string },
      success: true,
    }),
    vendor: "example",
    version: 1,
  },
};

export const processOrder = sqs({
  name: "processOrder",
  queue: "ordersQueue",
  message: orderMessageSchema,
  handler: async (batch) => {
    for (const message of batch.messages) {
      await processOrderMessage(message.body);
    }

    return batch.ok();
  },
});

export const functions = createFunctions({ processOrder });
```

Use `sqsQueue()` in config to define the AWS queue resource. Use `sqs({ queue: "ordersQueue" })` on a Function to attach that queue as a Lambda event source.

Local tests can send minimal body-first messages:

```ts
await functions.sendEvent("processOrder", {
  messages: [{ body: { orderId: "ord_1" } }],
  source: "sqs",
});
```

Each message body is serialized as JSON locally, parsed as JSON in the SQS runtime, and validated with the provided Standard Schema-compatible validator. Invalid JSON or schema failures become partial batch failures by default; use `sqs({ invalidMessageBody: "include" })` when a handler needs to inspect invalid messages directly.

Voke enables Lambda partial batch failure reporting for every synthesized SQS Event Source mapping. `batch.ok()` returns `{ batchItemFailures: [] }` unless validation already marked messages as failed, and `batch.batchResult().fail(message)` adds explicit per-message failures.

The v1 SQS boundary is intentionally small: Event Source Functions cannot mix with HTTP routes or invokable output contracts, event-source options are limited to batch size, maximum batching window, and enabled state, and DLQ/redrive configuration is deferred to the queue resource lifecycle.
