This page defines the words the rest of the documentation uses. After reading it, you know where each part of a Voke project lives and what `voke dev`, `voke build`, `voke synth` and `voke deploy` do with it.

## A project at a glance

```txt
voke.config.ts        name, stage, region, resources, provider: aws()
      │
      │ imported as config
      ▼
src/index.ts          the entrypoint
  createFunctions({   the Function Registry
    getUser: fn(...)          a Function with a Function Contract
    http: http({ routes })    a Function with routes from the Route Builder
    processOrder: sqs(...)    a Function with an SQS Event Source
  })
  export default voke(functions, { config })   the Gateway
```

The same project in code:

```ts twoslash
// @filename: voke.config.ts
import { aws } from "@vokejs/aws";
import { sqsQueue } from "@vokejs/aws/cloudformation";
import { defineConfig } from "voke";

export default defineConfig({
  name: "orders-api",
  provider: aws(),
  resources: {
    ordersQueue: sqsQueue(),
  },
});

// @filename: src/index.ts
import { sqs } from "@vokejs/aws";
import { schema } from "@vokejs/schema";
import { createFunctions, fn, http, route, voke } from "voke";

import config from "../voke.config";

const user = schema.object({ id: schema.string(), name: schema.string() });

const functions = createFunctions({
  getUser: fn({
    input: schema.object({ id: schema.string() }),
    output: user,
    handler: async ({ id }) => ({ id, name: "Ada" }),
  }),
  http: http({
    routes: [
      route.get("/users/:id", {
        params: schema.object({ id: schema.string() }),
        handler: (request) => ({ id: request.params.id }),
      }),
    ],
  }),
  processOrder: sqs({
    queue: "ordersQueue",
    message: schema.object({ orderId: schema.string() }),
    handler: async (batch) => batch.ok(),
  }),
});

// Typed call by registry key: the payload and the result follow the Function Contract.
const ada = await functions.invoke("getUser", { id: "usr_1" });

export default voke(functions, { config });
```

## Vocabulary

### `voke.config.ts`

The project settings: the project `name`, `stage`, `region`, the `entrypoint` path, `resources` such as queues and tables, and the Provider. `defineConfig()` from `voke` validates the settings and fills in defaults. Functions are not declared here: a `functions` setting fails with an error that points you to the entrypoint. See the [config reference](/docs/reference/config).

### Entrypoint

The module that declares the project's Functions. It is `./src/index.ts` unless `entrypoint` in `voke.config.ts` says otherwise. It exports either a Gateway (`export default voke(functions, { config })`) or, for a project without HTTP routes, the Function Registry (`export const functions = createFunctions({ ... })`).

### Function

A named unit of serverless work. Each Function becomes one AWS Lambda function when you deploy. There are three kinds:

- **Invokable**, made with `fn()`: other project code calls it by its registry key.
- **Route-backed**, made with `http()`: it serves HTTP routes through the Gateway.
- **Event Source**, for example `sqs()` from `@vokejs/aws`: an AWS service invokes it.

See [Functions](/docs/guides/functions).

### Function Registry

The typed catalog of the project's Functions, made with `createFunctions({ ... })`. The object keys (`getUser`, `http`, `processOrder` above) are the registry keys. Project code calls a Function through the registry with `functions.invoke("getUser", payload)`, and the payload and result are typed from the Function Contract. A project has one Function Registry.

### Function Contract

The input and output schemas of a Function (`input` and `output` on `fn()`). Voke validates the payload before the handler runs and the result after it returns. Any [Standard Schema](https://standardschema.dev) validator works; `@vokejs/schema` is Voke's own. See [Schemas](/docs/guides/schemas).

### Gateway

The HTTP side of the project, made with `voke(functions, { config })`. It serves the routes of the route-backed Functions, runs locally under `voke dev`, and answers requests in tests through `gateway.request("/path")`. When you deploy, the routes become an API Gateway HTTP API.

### Route Builder

`route.get()`, `route.post()` and the other HTTP methods on `route` from `voke`. Each call defines one route with its path, its handler, and optional `params`, `query`, `headers`, `body` and `output` schemas. You pass the routes to `http({ routes })`. See [HTTP routes](/docs/guides/http-routes).

### Provider

The platform adapter that builds, synthesizes, deploys and runs local infrastructure for the project. The first-party Provider is `aws()` from `@vokejs/aws`. A project has at most one Provider, and you set it only in `voke.config.ts` with `provider: aws()`. `voke build`, `voke synth`, `voke deploy`, `voke remove` and `voke local` fail with an error when no Provider is set. Function code stays the same whatever the Provider.

### Local AWS Provider

A program that emulates AWS services on your machine, so the queues, tables and other resources the project declares exist during development. Voke supports the AWS Emulator (the default) and Floci; choose Floci with `aws({ local: floci() })` and `floci` from `@vokejs/aws/local`. `voke local start` starts it. See [Local AWS](/docs/guides/local-aws).

<Callout type="info" title="Not the Provider">
  The Provider decides where the project deploys. The Local AWS Provider only
  emulates AWS locally.
</Callout>

### Runtime Variable

A value a Function loads at runtime from AWS Secrets Manager or SSM Parameter Store, declared with `secret()` or `parameter()` from `@vokejs/aws` in the Function's `variables`. The handler reads it through `context.variables.<key>.text()` or `.json()`. Runtime Variables are not part of the Function Contract. See [Runtime Variables](/docs/guides/runtime-variables).

### Event Source

A trigger where an AWS service invokes a Function. Voke supports SQS: `sqs({ queue, message, handler })` from `@vokejs/aws` attaches a queue that you declare in `resources`. The handler receives a batch of messages, and in tests you send one with `functions.sendEvent(...)`. See [SQS events](/docs/guides/sqs-events).

## What each command produces

| Command       | What it does                                                                                              | What it produces                                                                                                                          |
| ------------- | --------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `voke dev`    | Runs the entrypoint with `bun --hot` and serves the Gateway on `http://localhost:3000`.                   | A local API that reloads when you save.                                                                                                   |
| `voke build`  | Imports the entrypoint, generates one Lambda handler per Function, and bundles them through the Provider. | `dist/index.js` and `dist/voke-manifest.json`, which maps each Function to its Lambda handler.                                            |
| `voke synth`  | Imports the entrypoint and asks the Provider for a deployment template.                                   | A CloudFormation template, by default `dist/cloudformation.json`.                                                                         |
| `voke deploy` | Builds the project, uploads the bundle and the template, and creates or updates the stack.                | A CloudFormation stack named `<name>-<stage>`, the outputs printed to the terminal (the API URL first), and `.voke/outputs/<stage>.json`. |

See the [CLI reference](/docs/reference/cli) for every flag.

<Callout type="warn" title="The local stage is reserved">
  `voke deploy` refuses the stage `local`, which is reserved for local
  development.
</Callout>

## How Functions become Lambda handlers

You never write Lambda handlers yourself. Voke generates them from the Function Registry.

The entrypoint is the only place Functions are declared. `voke build`, `voke synth` and `voke deploy` import it to find them: the Gateway's registry when the default export is a Gateway, otherwise the `functions` export.

While the entrypoint loads for those commands, `process.env.VOKE_SYNTH` is `"1"`. Guard side effects, such as opening connections or starting servers, so they do not run during a build:

```ts twoslash
declare function connectToDatabase(): Promise<void>;
// ---cut---
if (process.env.VOKE_SYNTH !== "1") {
  await connectToDatabase();
}
```

`voke build` then writes `.voke/build/index.ts`, a generated module that exports one Lambda handler per Function, and bundles it, run-time code only, to `dist/index.js`. `dist/voke-manifest.json` records the handler of each Function.

Handler export names come from the registry keys:

- A key that is a valid JavaScript identifier keeps its spelling: `http` becomes the handler `index.http`.
- Any other key becomes camelCase: `process-order` becomes `index.processOrder`.
- Renaming a registry key renames its Lambda handler.

Deployed Lambda function names are `<name>-<stage>-<key>`, where `<name>` and `<stage>` come from `voke.config.ts`. For example, the key `getUser` in project `orders-api` on stage `dev` deploys as `orders-api-dev-getUser`. Set `name` on a Function to choose the deployed name yourself; the registry key stays the same.
