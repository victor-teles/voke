## Headline finding

Voke cannot put working code on AWS today. Four independent defects each block it:

1. `voke build` targets Bun; Node (the configured Lambda runtime) cannot load the bundle
   (`__require is not a function`).
2. The framework's runtime code uses `Bun.*` globals, so a Node-target bundle fails with
   `Bun is not defined`.
3. The synthesized template never sees Functions declared in the entrypoint, points Lambdas at
   handler files no build produces, emits `:param` route keys API Gateway does not understand,
   and has no deployed adapter for invokable or Request Authorizer Functions.
4. Deploy uploads no code: every Lambda contains a placeholder that answers 501, and a named API
   stage would make every route 404.

5. Since the package split, `voke synth` runs the `@voke/aws` copy of synthesis, but core keeps
   diverged copies of the AWS code. The live copy is missing the Runtime Variable IAM, so a
   deployed Function that reads a secret or parameter gets AccessDenied. No example sets
   `provider` in `voke.config.ts`, so `voke synth` fails for all of them.

`roadmap-v2.md` plans ten feature phases on top of a deploy path that does not exist yet. Plans
002–004 and 009 are the missing "phase 0"; the roadmap's priorities stay valid after them.

A scratch experiment showed the fix is tractable: with Bun globals replaced and the AWS SDK
externalized, the `hello-api` bundle drops from 1.13 MB to 109 KB, loads under Node 24, and
serves `GET /health` from an API Gateway v2 event.

## Dependency notes

- 009 comes first among the open plans. Core cannot import `@voke/*` (that would make a
  workspace cycle turbo rejects), so AWS behaviour reaches core only through the configured
  Provider. 009 ports what only core has (Runtime Variable IAM, `secret`/`parameter`, authorizer
  `variables`, the AWS variable loader) into `@voke/aws`, then deletes core's copies. It keeps
  core `cloudformation.ts`, `aws-lambda.ts` and `api.ts` frozen for `local.ts`/`e2e.ts` until 010.
- 003 requires 009 so it edits only `@voke/aws` (Lambda adapters, generated entry through
  `aws().build.plan`, route keys). It also moves the Provider to `voke.config.ts` only.
- 008 requires 009 and 003; it removes duplicate spellings, including new ones from the split.
- 004 requires 009 (IAM parity) and 003 (build manifest, provider in config). It adds a Provider
  deploy capability; 008 lands first because both edit `cloudformation-synthesis.ts`.
- 010 requires 009 and deletes the three files 009 left frozen. It runs after 004 in the order.
- 005 edits the same config, model and synthesis code as 003, 008 and 009, so it lands after them.
- 006 needs 004 (deploy), 008 (final command set) and 010 (`voke local` through the Provider).
- 007 requires 010. It uses 004's CloudFormation client only for its SDK bootstrap path and
  has a CLI fallback. It edits `cli.ts` like 006, so the two should not run at the same time.
- 011 has no prerequisite. It changes the schema result shape across core, `@voke/schema`,
  `@voke/aws` and most test files, so it should land before other work touches those tests.
- 012 does not need 011, but it runs after it so both proof pages compile against the final
  schema contract. It adds a `test` script to `@voke/docs`, which makes the root `bun run test`
  build the site.
- 013 requires 011 (the schema guide shows Zod and Valibot) and 012 (checked samples, link
  checking, registered MDX components). It must leave 012's legacy sample allowlist empty.
- 014 comes first in the Event Source track. Core is SQS-only today (`EventSourceDefinition`,
  `VokeModelEventSource`, the `"event"` case of `handlerFor`, synthesis). 014 opens that contract
  and moves SQS onto an internal adapter in `@voke/aws`; 015–017 only add adapters.
- 017 requires 015 because the S3 Event Source is built on the EventBridge rule code. A classic
  bucket notification would create a CloudFormation cycle (role → bucket → Lambda → role),
  because every Function role's policy references every resource.
- 016 and 017 both edit the `@voke/aws` adapter table and resource builders; do not run them at
  the same time.
- 018 has no hard prerequisite. It edits `handlerFor` and the Function loop in synthesis like
  014, and it adds an `invoke` option to `activateFunctionRegistry` that 019 extends, so it runs
  after 014 and before 019.
- 019 comes first in the Plugin track. Its `wrap` hook covers the durable path with no extra
  code, because 018 routes the deployed durable handler through `functions.invoke`.
- 020 requires 019 (Plugin Functions, `runtime.setup`, CLI commands). It also changes how the
  Function Contract Artifact reads JSON Schema, which changes artifact fingerprints once.
- 021 requires 019 (resource contributions, the wrap hook). It runs after 014 and 018 so its
  batch form matches the final SQS types and it can defer to `executionName` for Durable
  Functions.
- 022 comes first in the 022–034 round. It makes root `bun test` green and isolates every
  package's tests from the shell environment, so later executors start from a clean baseline.
  It wraps one CLI test in `process.chdir`; 026 may replace that with its `runCli(argv, { cwd })`.
- 023, 024 and 031 edit `packages/core/src/invoke.ts` and `remote.ts`. 023 changes run-time
  request handling and error mapping, 024 changes only types, and 031 moves the remote client
  out of core. Run them in that order. 023 leaves the Dev Function Invoke Endpoint's error
  bodies to 031.
- 025 and 026 edit `packages/core/src/cli.ts` (the `migrate` handler, then argument checking).
  025 takes the generated `package.json` from the scaffold; 034 owns the versions it writes.
- 027, 028 and 029 edit the resource and Function loops of
  `packages/aws/src/cloudformation-synthesis.ts`. 027 adds retention policies and the
  data-loss pre-flight. 028 adds dead-letter queues and copies 027's rule for which queues are
  retained. 029 rewrites how role statements are assembled, so it goes last of the three.
- 029 removes `bindResource` in favour of `context.resource(key)` and makes Plugin resources
  linked explicitly. 032 edits `@voke/idempotency` after it, so the table lookup has one
  shape by then.
- 030 splits `aws()` into a run-time and a deploy-time half with a package `imports` entry
  (`#provider`). It runs after 027–029 because they add deploy-time code that must stay out of
  the bundle. 033 adds a `runtime` member to the Provider, which stays in the run-time half.
- 034 runs last. It must keep 030's `imports` entry working in the published packages, and it
  publishes the export surface 031 leaves in `@voke/remote`.

Escape hatches that stay, one per layer: raw CloudFormation resource definitions in config, Hono
middleware on the Gateway, per-Function `synthesis` overrides, `build.external`, and the
`LocalProvider` interface.

ADRs created later by these plans take the next free number; three ADRs already share 0007
(`opinionated-framework`, `runtime-variables-and-aws-export-boundaries`,
`specialized-provider-and-helper-packages`).

The package split (`docs/adr/0007-specialized-provider-and-helper-packages.md`) also binds every
plan: `voke` is provider-neutral, and `@voke/aws` owns AWS runtime adapters, SQS and authorizer
entrypoints, local AWS helpers, and CloudFormation synthesis.

## Opportunities found but not planned yet

Ordered by how much they would add to "easy to use and deploy" once 001–006 land.

- **`voke logs --tail`, `voke invoke <function>`, `voke event <function>`.** After a deploy the
  next question is "what did it do?". Roadmap v2 phase 4 lists local invoke and event as P0; add
  the deployed variants and log tailing.
- **Parameters and secrets.** Runtime Variables landed on `main`; plan 009 makes them work when
  deployed. Remaining scope tracked as issue #36 and roadmap v2 phase 1.
- **Data safety on `voke remove`.** Now plan 027 (retention policies and a data-loss
  pre-flight). Still unplanned: `protect` for a stage, `voke remove --delete-data`, and a
  command to adopt a retained resource into a new stack.
- **Least-privilege resource linking.** Now plan 029. Still unplanned: read-only links, a
  custom grant escape hatch, `voke resources`, and config keys typed into the entrypoint so a
  misspelled link is a compile error.
- **Cross-Lambda `functions.invoke`.** The AWS transport calls `definition.name ?? definition.key`
  (`packages/core/src/invoke.ts:878-879`) while deployed Lambdas are named
  `<name>-<stage>-<key>` (`model.ts:460-463`); the role has no `lambda:InvokeFunction` grant; and
  `VOKE_INVOKE_RUNTIME=aws` is never set in the template. After plan 003, deployed code invokes
  sibling Functions in-process, which works because all Functions share one bundle. True
  cross-Lambda invocation needs its own plan.
- **Local event delivery.** After plan 007, queues live in the emulator but nothing delivers
  their messages to local Functions. A `voke dev` poller that feeds `functions.sendEvent` would
  make SQS flows work locally end to end. The same idea extends to schedules and EventBridge.
  Plans 015–017 add SNS, EventBridge, Schedule, stream and S3 sources, which are testable
  locally only through `functions.sendEvent` until this exists.
- **Full local deploy.** AWS Emulator 1.0.367 can run simple Lambda handlers, but its JavaScript
  runtime lacks `Request`/`Response` and several `node:` modules, so a Voke bundle does not load
  there. When that changes, point the plan 004 pipeline at the emulator endpoint. The Floci
  bootstrap still deploys the 501 placeholder (`packages/core/src/local-provider.ts:109-126`).
- **Typed publishers.** Send to a queue, topic or event bus with the schema the consuming
  Function declares. Deferred from the 014–021 round by owner choice.
- **Observability Plugin.** Structured logger, metrics and tracing on plan 019's wrap hook
  (roadmap v2 phase 8). Deferred from the 014–021 round by owner choice.
- **Durable execution tooling.** `voke executions` (list, inspect, stop), callback helpers, and
  pruning of retained Lambda versions. Plan 018 defers all three.
- **DLQ and redrive.** Now plan 028. Still unplanned: a `voke` command to read or redrive a
  dead-letter queue, delivery-side dead-letter settings for SNS subscriptions and EventBridge
  targets, and a destination that keeps a stream record's payload (a stream's dead-letter
  message holds a pointer to the batch, not the records).
- **Isolated emulator per test run** (`aws-emulator -p 0`) in `voke/testing`.
- **Deploy-time code in the Lambda bundle.** Now plan 030. Since plan 019 the generated Lambda
  entry imports `voke.config.ts`, and `aws()` eagerly imports its deploy, synthesis, local and
  build code: `examples/hello-api` builds to 279 KB. Dynamic `import()` does not fix it (Bun
  inlines the module), so plan 030 uses a build condition instead.
- **Confirm S3 key encoding** with a captured S3 → EventBridge event before the first release
  (plan 017, ADR 0013). If AWS URL-encodes keys, switch `s3()` to decoding.
- **Real-AWS proof for Durable Functions** (plan 018, step 8): the managed runtime's SDK commands,
  re-execution after suspension, the synchronous invoke response, and Node 22.
- **Lambda Function URLs and response streaming** as a cheaper, simpler alternative to API
  Gateway for single-Function APIs.
- **Personal and preview stages, CI workflow generator** (roadmap v2 phase 7). The reserved
  `local` stage in plan 004 is the first step; a per-developer default stage would remove the
  `--stage` flag from the happy path.
- **Custom domains** for HTTP APIs.
- **Friendlier Function options**: top-level `timeout`/`memory` on `fn`/`http`/`sqs` instead of
  the `synthesis` bag.
- **Source maps and per-Function bundles** (roadmap v2 phase 6).
- **Reproducible docs builds**: fixed since this was written; `apps/docs/package.json` no longer
  uses `latest` (checked while planning 034).

Found by the 2026-11-15 audit and not planned in 022–034. The first group was reproduced or
read end to end; verify each before planning it.

- **Invocation options.** `timeoutMs` never clears its timer, so a process stays alive for the
  full timeout after a fast call; `retries` repeats deterministic validation failures with no
  backoff; a timed-out attempt keeps running and can overlap its retry
  (`packages/core/src/invoke.ts`, around lines 1530–1565). The trace state is a module-level
  array (`invoke.ts:827`), so two concurrent invocations can see each other's trace;
  `AsyncLocalStorage` would fix it (plan 029 introduces one in core for Resource Links).
- **Cross-Lambda `functions.invoke` with an explicit `runtime: "aws"`.** That path wraps the
  payload as `{ payload, trace }` (`invoke.ts`, `invokeAws`, `envelope: true`), while the
  deployed handler validates the whole Lambda event as the payload
  (`packages/aws/src/lambda-handlers.ts:219-223`). The Provider-routed path sends the bare
  payload and is not affected. `unwrapPayload` also strips any result that has a `data` key.
- **Deploy pre-flight for AWS limits.** Nothing checks the 1 MB template limit, the
  500-resource limit (plan 028 adds one or two resources per Event Source Function), 64-character
  Function names or the 250 MB unzipped code limit before CloudFormation rejects the deploy.
- **`voke deploy --dry-run` changes the account.** It creates the bootstrap stack and uploads
  the bundle and the template before the dry-run flag is read
  (`packages/aws/src/deploy.ts`, `ensureArtifactBucket` and the upload before `deployStack`).
- **Stack states the deploy does not handle**: `CREATE_FAILED`, `ROLLBACK_FAILED` and
  `DELETE_FAILED` fall through to an update change set.
- **Artifact bucket growth.** The bootstrap bucket has no lifecycle rule, and
  `durable-synthesis.ts` retains every published version of a Durable Function.
- **An explicit Function `name` drops the stage** (`packages/core/src/model.ts`,
  `definition.name ?? generatedFunctionName(name)`), so a second stage collides on the Lambda
  name.
- **Lambda Request Authorizer cache key.** With `cacheTtlSeconds > 0` the cache key is only the
  identity source, while the handler also receives the path and method; a path-dependent
  decision would be replayed across routes. Read, not confirmed against AWS.
- **Hardening defaults**: no Kinesis `StreamEncryption`, no point-in-time recovery option for
  tables, no access logs or throttling on the HTTP stage, no reserved concurrency, no FIFO
  queues.
- **HTTP details plan 023 leaves alone**: 405 with `Allow` (needs an `ANY` route per path in
  synthesis, so local and deployed agree), `HEAD` on a `GET` route (answers 200 locally;
  deployed behaviour unconfirmed), form, multipart and text body parsers, a cookie object, and
  a status code for a validated result (a typed result is always 200 today).
- **CLI features plan 026 leaves alone**: `--json`, `--verbose`, `--cwd`, distinct exit codes,
  and `--config` in another directory still resolving the entrypoint against the working
  directory.
- **Test coverage of small packages**: `@voke/http` has no tests, `@voke/testing` has one.
- **Node consumers.** `import("voke")` fails on Node (extensionless imports in TypeScript
  source). ADR 0007 makes Node-only toolchains a non-goal; plan 034 keeps that.

## Findings considered and rejected

- Put the Function Registry in `voke.config.ts` so synth can see it: rejected, it contradicts the
  roadmap principle "Do not move Function composition into `voke.config.ts`" and ADR 0007. Plan
  003 imports the entrypoint instead and removes the config-first registry.
- Keep removed options as deprecated aliases for a release: rejected. The package is unreleased
  (version `0.0.0`); ADR 0005 and ADR 0007 both say to remove without aliases.
- Require users to write `export const handler = ...` per Function: rejected, it is the AWS glue
  the framework exists to remove. Plan 003 generates the entry module.
- Keep shelling out to `aws cloudformation package`/`deploy`: rejected as the default because it
  keeps the AWS CLI as a prerequisite and gives no structured progress or errors. It remains the
  fallback if the SDK dependency decision goes the other way.
- Run Bun on Lambda through a custom runtime or layer instead of targeting Node: deferred. It
  adds a layer to manage and slower cold starts for no user-visible gain today; the config
  already restricts runtimes to `nodejs22.x` and `nodejs24.x`.
- Keep the named API Gateway stage and strip the stage prefix from `rawPath` in the adapter:
  rejected in favor of the `$default` stage, which removes the problem and gives cleaner URLs.

- A Step Functions state machine builder or a typed workflow DSL: rejected by the owner on
  2026-11-14 in favor of durable functions (plan 018). A state machine can still be declared as
  a raw CloudFormation resource.
- Classic S3 bucket notifications for the S3 Event Source: rejected, they create a
  CloudFormation dependency cycle with the shared resource policy. Plan 017 uses EventBridge.
- Plugins declared on `voke(functions, { plugins })`: rejected. Registry-only projects have no
  Gateway call, and the CLI needs Plugins at synth time. Plan 019 declares them in
  `voke.config.ts`, like the Provider.

- Answer 405 locally for a wrong method (plan 023): rejected. The deployed HTTP API has one
  route key per method and path, so API Gateway answers 404 before any Function runs; a local
  405 would make `voke dev` disagree with production.
- Load `aws()` capabilities with dynamic `import()` (plan 030): rejected after measuring. Bun
  1.4.4 inlines the dynamically imported module into the bundle, or emits it as a chunk with
  `--splitting`; either way the code ships.
- A positional stage, `voke deploy prod` (plan 026): rejected. ADR 0007 allows one spelling;
  the command fails with a usage error that names `--stage`.
- A Serverless variable resolver in the migrator (plan 025): rejected. Only literal values are
  copied; anything else is omitted and reported.
- Changesets for versioning (plan 034): rejected for now. Versions are lockstep and there is
  one maintainer, so a small script and a hand-written changelog do the job without a
  dependency.
- Validate `expiresAfterSeconds` against the Function timeout (plan 032): rejected. The defect
  is the expiry value written for an in-progress record, which plan 032 fixes directly.
- Retain queues, streams and topics on delete (plan 027): rejected. Their records are in
  transit with a bounded lifetime, and a retained queue has no consumer left to read it.
